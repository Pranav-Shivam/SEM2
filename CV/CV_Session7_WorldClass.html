Local Features & Robust Fitting
SIFT · RANSAC

How a photograph gets reduced to a few hundred distinctive, matchable points — and how you fit a model to those matches when a large fraction of them are simply wrong.

How to read this guide

Session 7 covers two ideas that are taught back-to-back because they are used back-to-back in practice: SIFT (Scale-Invariant Feature Transform) tells you what to match between two images — a sparse set of distinctive, repeatable points, each carrying a descriptor vector. RANSAC (Random Sample Consensus) then tells you how to trust the resulting matches enough to fit a geometric model (a line, a homography, a fundamental matrix) even though many of those matches will be wrong.

This guide keeps the two halves in the order the source material presents them — local features first, robust fitting second — but repeatedly cross-references how they compose into a single working pipeline: detect → describe → match → fit robustly.

01

Why Local Features Matter

Foundations

Intuition first — three steps turn "two photos" into "one panorama"

Take two overlapping photographs of the same scene taken from slightly different positions. To stitch them into one panorama, a computer needs to figure out how the second image is rotated, scaled, and shifted relative to the first — and it can't do that from raw pixels directly, because pixels shift entirely as the camera moves. The fix is a simple three-step recipe that underlies panorama stitching and a great deal of the rest of computer vision:

  1. Extract features

    Find a sparse set of distinctive, repeatable points in each image — corners, blobs, textured patches — points that a detector will find again even if the image is rotated, scaled, or slightly relit.

  2. Match features

    For each feature in image A, find its most similar counterpart in image B by comparing descriptor vectors — turning "which pixels correspond?" into a nearest-neighbor search problem.

  3. Align images

    Use the matched point pairs to solve for the geometric transformation (translation, homography, etc.) that maps one image onto the other — this is exactly where RANSAC enters, because many of the "matches" from step 2 will be wrong.

Applications — the same recipe, many domains

ApplicationWhat local features provide
Panorama / image stitchingCorrespondences to solve for the homography that aligns overlapping views

Why This Matters — four properties that make local features useful

Locality: because each feature only depends on a small image patch, features are individually robust to occlusion and clutter elsewhere in the image — losing half the scene still leaves plenty of features intact.

Quantity: a single image typically yields hundreds to thousands of features, giving redundancy: even if many individual matches are wrong or missed, enough good ones usually survive to solve the alignment problem.

Distinctiveness: a good descriptor should be different enough across genuinely different patches that nearest-neighbor matching reliably finds the true correspondence rather than a lookalike.

Real-time efficiency: detection, description, and matching are all designed to be fast enough to run live — a requirement inherited directly by every downstream use case (AR, SLAM, robotics) that cannot afford to "pause the world" while it computes.

02

Invariance Requirements

Foundations

Intuition first — the same physical point, seen differently

The whole point of a local feature is that the same physical point in the world should produce a matchable feature no matter how the camera or the lighting changed between two shots. That requirement splits cleanly into two families of invariance a detector/descriptor must survive.

The two invariance families
Geometric invariance — survives changes in camera viewpoint/pose · Translation — the object moves within the frame · Rotation — the camera or object rotates in-plane · Scale — the camera moves closer/farther, changing apparent size Photometric invariance — survives changes in illumination/imaging · Brightness — the whole scene gets darker/lighter · Exposure — the camera's exposure setting changes · Contrast — the dynamic range of intensities changes

How SIFT delivers each invariance

Invariance neededSIFT mechanism
TranslationLocal detection — a feature is defined relative to its own neighborhood, not absolute image coordinates
ScaleSearching for extrema across the scale-space / DoG pyramid (Section 04) — each keypoint is found at its own characteristic scale
RotationAssigning a canonical dominant orientation to each keypoint (Section 06) and describing gradients relative to it
Brightness / contrastNormalizing the final descriptor vector (unit length, then clamping and renormalizing) so uniform illumination changes cancel out
Exam Radar

Invariance — exam radar

  • Keep the two families straight: geometric (translation, rotation, scale) vs photometric (brightness, exposure, contrast) — a question may ask you to classify a given change into the right family.
  • Every invariance claim maps to a specific mechanism in the pipeline — don't just say "SIFT is scale invariant," be ready to say why (scale-space search) and where in the four-stage pipeline it happens.
03

The Three Core Components

Foundations

Every local-feature method decomposes into the same three jobs

Regardless of the specific algorithm (SIFT, ORB, SURF, learned descriptors), a local-feature pipeline always separates into three distinct sub-problems, each with its own success criterion.

  1. Detection

    Find repeatable interest points — locations that a detector will re-find in a second image of the same scene, despite viewpoint or lighting changes. Repeatability, not "interestingness" in any human sense, is the success metric.

  2. Description

    Extract a numeric vector descriptor summarizing the local appearance around each detected point, invariant to the transformations listed in Section 02, and distinctive enough to distinguish genuinely different points.

  3. Matching

    Given descriptor sets from two images, find correspondences — typically by nearest-neighbor search over descriptor vectors — to hand off to a robust geometric fitting step such as RANSAC.

A widely used refinement at the matching stage — beyond plain nearest-neighbor lookup — is Lowe's ratio test: for each descriptor in image A, compare the distance to its best match in image B against the distance to its second-best match, and accept the match only if the best is meaningfully closer (e.g. ratio < 0.8). This filters out ambiguous matches where a point has several near-equally-good candidates, which are disproportionately likely to be wrong and would otherwise pollute the correspondence set handed to RANSAC.

04

Scale-Space & the Difference of Gaussians

SIFT — Stage 0

Intuition first — "what scale is this blob at?"

A stop sign photographed from 2 meters away and the same stop sign photographed from 20 meters away are the same object at two different apparent sizes. To detect it reliably regardless of distance, SIFT doesn't search only over image location (x, y) — it searches over a third axis too: scale (σ). The image is progressively blurred with Gaussians of increasing σ, and interest points are sought as extrema across this combined (x, y, σ) volume, so that each detected keypoint comes with its own characteristic scale baked in.

Difference-of-Gaussians (DoG)
D(x, y, σ) = [G(x, y, kσ) − G(x, y, σ)] * I(x, y) G(x,y,σ) = a 2-D Gaussian blur kernel of standard deviation σ k = a fixed multiplicative scale step between adjacent Gaussian-blurred images I(x,y) = the input image D(x,y,σ) = the image blurred at scale kσ, minus the same image blurred at scale σ

Why Difference-of-Gaussians instead of Laplacian-of-Gaussian?

The theoretically "ideal" blob detector is the scale-normalized Laplacian of Gaussian (LoG) — it responds maximally at a blob's true characteristic scale and location. But computing a LoG response at every pixel and every scale directly is expensive: it requires convolving the image with a fresh second-derivative-of-Gaussian kernel at each scale.

DoG approximates LoG almost for free. If you're already building a pyramid of Gaussian-blurred images at increasing σ (which many pipelines need anyway), then the difference between two adjacent Gaussian-blurred images is a close numerical approximation to the scale-normalized LoG — and computing it costs only a pixel-wise subtraction, no new convolution. Extrema in the resulting 3-D (x, y, σ) DoG volume identify blobs detected at their own natural scale.

This "3×3×3 minus the center pixel = 26 comparisons" test is exactly Lowe's original 2004 formulation. 05

SIFT Stage 1-2 — Extrema Detection & Keypoint Localization

SIFT — Stages 1-2

The four-stage SIFT pipeline, at a glance

Lowe's SIFT (2004, University of British Columbia) runs as four sequential stages. Sections 05-06 of this guide walk through all four in order.

  1. Scale-space extrema detection

    Search across location and scale simultaneously using the Difference-of-Gaussians pyramid; flag candidate keypoints as local extrema among their 26 neighbours (Section 04).

  2. Keypoint localization

    Refine each candidate's position and scale; reject low-contrast points and points that sit on an edge rather than a true corner/blob.

  3. Orientation assignment

    Build a local gradient-orientation histogram and assign the dominant peak as the keypoint's canonical orientation, enabling rotation invariance.

  4. Keypoint descriptor

    Build a 128-dimensional gradient-orientation descriptor in the rotated, scaled frame, then normalize it for illumination invariance.

Stage 2 in detail — throwing away unreliable candidates

Not every scale-space extremum makes a good keypoint. Localization does two further jobs beyond simply confirming "this point is an extremum":

Low-contrast rejection: a candidate whose DoG response magnitude |D(x)| is below a fixed threshold is discarded — a weak response is more likely to be noise than a genuine, stable structure, and would not survive re-detection under a slightly different image or lighting.

Edge rejection (the Hessian ratio test): a point lying along a straight edge is poorly localized along the edge direction — its DoG response is strong in one direction but nearly flat in the perpendicular direction, so its exact position along the edge is ambiguous and unstable. This is tested with the 2×2 Hessian matrix of second derivatives at the candidate:

Edge response test — principal curvature ratio
H = [ Dxx Dxy ; Dxy Dyy ] (Hessian of the DoG response at the candidate) Trace: Tr(H) = Dxx + Dyy = α + β Determinant: Det(H) = DxxDyy − Dxy² = αβ Reject the point as edge-like if: Tr(H)² / Det(H) > (r + 1)² / r (commonly r = 10) where α, β are the two principal curvatures (eigenvalues of H). A true corner/blob has α ≈ β; an edge has one curvature much larger than the other, making the ratio blow up.
Exam Radar

Localization — exam radar

  • Two independent rejection tests exist at this stage — low-contrast and edge response. A question may ask which specific test would reject a given example point; check both, they are not interchangeable.
  • Common mistake: assuming any extremum found in Stage 1 automatically becomes a keypoint. In practice, a large fraction of Stage-1 candidates are pruned here.
  • The edge test uses only the ratio Tr(H)²/Det(H), not the raw eigenvalues — this makes it scale-independent (it only cares about the relative shape of the local curvature, not its absolute magnitude).
06

SIFT Stage 3-4 — Orientation Assignment & the 128-D Descriptor

SIFT — Stages 3-4

Stage 3 — giving every keypoint a canonical "up"

Rotation invariance in SIFT does not come from a rotation-invariant descriptor formula — it comes from a much simpler trick: cancel the rotation before describing the point. Around each keypoint, gradient orientations are computed over a local neighborhood, weighted by their gradient magnitude and by a Gaussian window centered on the keypoint (so nearby pixels count more than far ones). These weighted orientations are accumulated into a histogram; the histogram's dominant peak becomes the keypoint's canonical orientation. From then on, everything about the descriptor is measured relative to this orientation, so rotating the whole image simply rotates the assigned canonical direction along with it — the relative geometry, and hence the descriptor, stays the same.

If the orientation histogram has more than one strong peak (a second peak within roughly 80% of the tallest one — common at corners where multiple edges meet), a separate keypoint is created for each dominant peak, all sharing the same location and scale but each with its own orientation. This trades a small increase in keypoint count for much greater matching stability at genuinely ambiguous points.

Stage 4 — turning the neighborhood into 128 numbers

Once position, scale, and orientation are fixed, the descriptor is built entirely in that keypoint's own local, rotated, scaled reference frame: the neighborhood around the keypoint is divided into a 4×4 grid of spatial subregions, and within each subregion, the local gradient orientations are accumulated into an 8-bin orientation histogram (again weighted by gradient magnitude and a Gaussian window). Concatenating all 16 subregions' 8-bin histograms gives the final descriptor.

Descriptor dimensionality
4 × 4 spatial grid × 8 orientation bins = 128-dimensional descriptor vector Illumination invariance: the 128-D vector is normalized to unit length, so a uniform brightness/contrast scaling of the whole patch cancels out. Non-linear illumination robustness: any single component larger than a fixed clip threshold is capped, and the vector is renormalized — this limits the influence of a few very bright gradients (e.g. specular highlights) that a simple linear brightness change would not explain.

07

RANSAC — Robust Model Fitting

RANSAC

Intuition first — why not just fit to all the matches?

Feature matching (Section 03) is noisy: some fraction of the "matches" between two images are simply wrong — a repeated texture, an ambiguous descriptor, a genuinely unmatched point paired up anyway. Ordinary least-squares fitting is extremely sensitive to such outliers — a single bad match can drag a fitted line or homography far from the truth. RANSAC sidesteps this by never trusting all the data at once: it repeatedly guesses a model from a tiny random subset, and lets the full data vote on which guess was right.

The four-step iterative process

  1. Sample

    Randomly pick the minimum number of points needed to define the model — 2 points for a line, 4 point-correspondences for a homography.

  2. Solve

    Fit the model exactly to that minimal sample (a closed-form solve — two points determine a line, four correspondences determine a homography).

  3. Score

    Count inliers — how many of all the data points lie within a preset distance threshold of the fitted model.

  4. Repeat & keep best

    Repeat steps 1-3 many times; retain whichever sampled model achieved the most inliers. Optionally, re-fit the model one final time using all of that best model's inliers together, for a more accurate final estimate.

Key principle

"All good matches are alike; every bad match is bad in its own way." Correct correspondences all agree with the same true geometric transformation — they form a consensus. Incorrect correspondences are wrong essentially at random, and rarely agree with each other on any single alternative model. This asymmetry is exactly what lets RANSAC tell inliers from outliers: inliers cluster around one model, outliers scatter.

RANSAC loop — exam radar

  • Memorize the exact order: Sample → Solve → Score → Repeat & keep best. A shuffled-order multiple-choice question is a common trap.
  • Know the minimal sample size cold: 2 points for a line, 4 correspondences for a homography — other models (fundamental matrix: 7 or 8 points, depending on the solver) may appear as a numerical twist.
  • "Scoring" always means counting inliers under a fixed distance threshold — it is not the same as minimizing total fitting error over all points, which is what the final optional re-fit step does instead.
08

RANSAC — Parameters, Guarantees & Applications

RANSAC

How many iterations are enough?

Running "many" trials is not a free parameter to guess at — it can be derived from how bad you expect the data to be. If e is the expected fraction of outliers and s is the minimal sample size for the model, then the probability that a single random sample is entirely outlier-free is (1−e)^s, and the probability that none of N independent trials draws an all-inlier sample is (1 − (1−e)^s)^N. Setting that failure probability to 1 − p (where p is the desired probability of success) and solving for N gives the standard formula:

Required number of RANSAC iterations
N = log(1 − p) / log(1 − (1 − e)^s) p = desired probability that RANSAC succeeds (finds at least one all-inlier sample), e.g. 0.99 e = expected fraction of outliers in the data s = minimal sample size for the model (2 for a line, 4 for a homography) Worked example (line, s=2, p=0.99, e=0.4): N = log(0.01) / log(1 − 0.6²) = log(0.01) / log(0.64) ≈ 10.3 → round up to 11 iterations Worked example (homography, s=4, p=0.99, e=0.5): N = log(0.01) / log(1 − 0.5⁴) = log(0.01) / log(0.9375) ≈ 71.4 → round up to 72 iterations

The other free parameter — how big should the inlier threshold be?

RANSAC's distance threshold decides who counts as an inlier during scoring. It should reflect the expected measurement noise in the data — commonly modeled as Gaussian — rather than being picked arbitrarily. A typical rule of thumb used for point-correspondence problems is a threshold around ~3 pixels, tight enough to reject genuinely wrong matches but loose enough to tolerate ordinary localization noise in a correct match.

Guarantees, limitations & where RANSAC is used

AspectDetail
Reliability guaranteeWorks reliably when outliers make up less than 50% of the data
StrengthsSimple to implement; general-purpose — applies to line/plane fitting, homography estimation, fundamental matrix estimation
WeaknessesRequires tuning (threshold, iteration count); needs many iterations as outlier fraction grows; fails at very low inlier ratios (near or above 50% outliers)
ApplicationsImage alignment / panorama stitching, 3D reconstruction, motion/translation estimation, homography estimation
Exam Radar

Parameters & limits — exam radar

  • Be ready to plug numbers into N = log(1−p) / log(1−(1−e)^s) directly — this exact numerical computation is a very likely exam question, in either direction (given e,s,p find N; or given N,s,p find max tolerable e).
  • Common mistake: forgetting that N grows extremely fast with e and s — doubling s does not merely double the required iterations, it raises them by orders of magnitude at high outlier fractions.
  • "Works reliably below 50% outliers" is the single most quotable limitation of RANSAC — know it as a number, not just a vague qualitative statement.
09

Conceptual Deep Dives

Compare & Contrast
If LoG is the "ideal" blob detector, why does every practical SIFT implementation use DoG instead?

  1. LoG requires convolving the image with a fresh second-derivative-of-Gaussian kernel at every scale you want to search — a genuinely new, relatively expensive convolution per scale level.

  2. DoG only needs a subtraction between two Gaussian-blurred images that a scale-space pipeline is typically building anyway — the marginal cost of computing DoG at every level is essentially one array subtraction.

  3. Because DoG is a close numerical approximation to the scale-normalized LoG (both are derived from the same underlying heat-equation-like diffusion process in scale-space), the accuracy loss from substituting one for the other is small relative to the compute savings.

Key Insight

DoG is not "a different algorithm" from LoG — it's an efficient finite-difference approximation to the same underlying scale-space derivative. Recognizing this relationship, not just the two names, is what exam questions probe for.

Why does SIFT's descriptor use a 4×4 spatial grid with 8 orientation bins rather than something coarser or finer?

  1. A coarser grid (say 2×2) would be less sensitive to small positional misalignment after orientation normalization, but would throw away too much spatial structure to be distinctive — many different patches would look identical.

  2. A much finer grid (say 8×8) would capture more spatial detail, but would become brittle to the same small misalignments it's trying to describe, and would balloon the descriptor's dimensionality (8×8×8 = 512) with diminishing distinctiveness returns.

  3. 4×4×8 = 128 was Lowe's empirically chosen balance point: enough spatial and angular resolution to be highly distinctive, while still tolerant of the residual pose error left over after Stage 3's orientation normalization.

Key Insight

Every dimensionality choice in a hand-crafted descriptor is a distinctiveness-vs-robustness trade-off — the same tension that motivates learned descriptors (which let training data pick the balance instead of a fixed formula).

Why can't you just fit a line/homography to all the matched points with ordinary least squares instead of running RANSAC?

  1. Least-squares minimizes the sum of squared residuals over every point, including outliers — squaring means a single very-wrong outlier contributes an outsized share of the total error, pulling the fitted model toward it.

  2. RANSAC never fits to all the data at once — it fits to a minimal, hopefully outlier-free sample, and only afterward checks how many of the remaining points agree. Outliers can only hurt the score of whichever trial happened to sample them, not distort every trial's fit.

  3. The two techniques are complementary, not competing: a common final step re-runs ordinary least squares, but only on the inlier set RANSAC identified — getting least-squares' precision without its outlier sensitivity.

Key Insight

RANSAC is best understood as an outlier-rejection wrapper around a plain fitting method, not a replacement for one — "sample-and-vote," then "fit cleanly" on what voting found.

Key Takeaways & Exam Tips

Key Takeaways

The local-features pipeline is always detect → describe → match: whatever the specific algorithm, these three jobs stay separate, each with its own success criterion (repeatability, distinctiveness, efficient correspondence search).

SIFT's sequence: DoG scale-space extrema detection → keypoint localization (contrast + edge rejection) → orientation assignment → 128-D descriptor. Know the order and what each stage fixes about the previous one's raw output.

DoG approximates LoG almost for free, by subtracting adjacent Gaussian-blurred images; extrema in the resulting 3-D (x, y, σ) volume identify blobs at their own characteristic scale.

RANSAC's loop: sample the minimal set → fit → count inliers → iterate → keep the best model (optionally re-fit on its inliers). It is robust as long as outliers stay under roughly 50% of the data.

Exam pattern: this session mixes theory questions (name the stage, name the invariance, explain why a design choice was made) with numericals (compute the descriptor dimensionality, compute a RANSAC iteration count, evaluate the edge-rejection ratio) — expect both, and practice the arithmetic, not just the concepts.

Exam Radar

Highest-yield numericals to drill before the exam

  • Descriptor dimensionality arithmetic: 4×4×8 = 128, and being able to redo it for a hypothetical different grid/bin count.
  • The 26-neighbour rule for scale-space extrema (8 same-scale + 9 above + 9 below), and correctly identifying whether a given toy grid of values is a max, a min, or neither.
  • Plugging numbers into N = log(1−p) / log(1−(1−e)^s) for both lines (s=2) and homographies (s=4), in both directions (solve for N, or solve for the maximum tolerable e given a fixed N).
  • The edge-rejection ratio test Tr(H)²/Det(H) > (r+1)²/r — know what large vs small ratios mean physically (edge vs corner/blob), even if you are not asked to compute exact eigenvalues.
  • Stating RANSAC's ~50% outlier-tolerance limit precisely, and being able to justify it qualitatively from the iteration-count formula (as e → 1, N explodes).

Why does SIFT create multiple keypoints at the same location/scale when the orientation histogram has two comparably strong peaks?

  • BBecause the DoG extrema test failed and needs a second attempt

  • DTo compensate for low contrast at that point
At corners or junctions with two comparably strong gradient directions, picking one arbitrarily would make the resulting descriptor sensitive to noise that tips the histogram one way or the other between images — creating a keypoint per strong peak keeps both interpretations available for matching. A is false — each resulting keypoint is still exactly 128-D. B and D confuse this with the earlier extrema/contrast tests, which are unrelated to orientation.Common mistakeThinking of this as an error-recovery mechanism rather than a deliberate robustness trade-off (more keypoints, each more stable).
Q8HardRANSAC key principle
"All good matches are alike; every bad match is bad in its own way" is the reasoning behind which step of RANSAC?
  • ASample — picking the minimal random subset
  • BScore — counting inliers against a fitted model
  • CSolve — fitting the model to the minimal sample
  • DNone of the steps; it is unrelated to the algorithm mechanics
Scoring works precisely because inliers all agree with the same correct model (they cluster, "alike"), while outliers each disagree with it differently (they scatter, "in their own way") — that separation is what makes counting points within a distance threshold a meaningful way to distinguish a good model from a bad one. A and C are mechanical steps that don't depend on this asymmetry to function.Common mistakeTreating the quote as a general remark about the data rather than tying it to the specific mechanism (scoring/counting inliers) it justifies.
Q9HardOutlier limit
Why does the required iteration count N explode as the outlier fraction e approaches 1, rather than growing gently?
  • ABecause the inlier threshold must also shrink as e grows
  • BBecause N is defined as a linear function of e
  • CIt doesn't — N grows linearly with e in practice
  • DBecause (1−e)^s shrinks exponentially in s, and N depends on the logarithm of (1 − that already-tiny number), which blows up as (1−e)^s → 0
As e→1, (1−e)^s→0, so log(1−(1−e)^s)→log(1)=0 — dividing by a value approaching zero drives N to infinity. This is why RANSAC's practical reliability is bounded: at very high outlier fractions, no realistic iteration budget finds an all-inlier sample often enough. A confuses two independent parameters. B and C both mischaracterize N's relationship to e as linear, when it is governed by an exponential-then-logarithm structure.Common mistakeAssuming iteration-count requirements scale gently/linearly with data quality — the formula's structure means they don't, especially as e crosses 50%.
Q10HardFull pipeline
In a panorama-stitching pipeline, which statement correctly places SIFT and RANSAC relative to each other?
  • ASIFT detects/describes/matches candidate correspondences first; RANSAC then robustly fits the homography from those (noisy) correspondences
  • BRANSAC first cleans the raw pixels; SIFT then detects keypoints on the cleaned image
  • CSIFT and RANSAC are two competing alternatives for the same step — a pipeline uses one or the other, never both
  • DRANSAC replaces the need for a descriptor entirely, matching keypoints directly by pixel location
SIFT produces the raw material (keypoint correspondences, some of them wrong) that RANSAC needs as input — RANSAC cannot run without a candidate correspondence set to sample from, and SIFT alone cannot safely estimate a global geometric transform in the presence of mismatches. They are sequential and complementary, not competitors. B and D invert or eliminate the actual dependency; C denies that they solve different problems (feature correspondence vs. robust geometric fitting).Common mistakeStudying SIFT and RANSAC as two disconnected topics rather than as adjacent stages of one working pipeline — most application-style exam questions test exactly this connection.

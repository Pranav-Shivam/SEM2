This page covers the Optional Topic: Face Detection & OCR from CS2-25 AIMLCZG525. 01

Face Detection vs Recognition vs Verification

Optional Topic — Course Notes

Intuition first — three different questions, three different jobs

Detection only answers "is there a face here, and where?" — its output is a bounding box (and, in modern detectors, a handful of facial landmarks), with no notion of identity at all. It's the same underlying task as the generic object detection you already studied, just specialized to one object category with far more regular geometry.

Recognition / identification takes a detected face and answers "whose face is this?" — a 1:N matching problem, comparing the probe face against every enrolled identity in a gallery (e.g. every employee on a company roster) and returning the closest match (or "unknown" if nothing is close enough).

Verification is narrower and stricter: it answers a yes/no question — "is this face the same person as the one it claims to be?" — a 1:1 matching problem, comparing exactly one probe against exactly one claimed identity's stored template. Unlocking a phone with your own enrolled face is verification; a police lineup search across a database is identification.

The attendance-system pipeline — detect, align, embed, match

  1. Detect

    Locate every face's bounding box (and landmarks) in the incoming camera frame — via a classical detector like Viola-Jones or a modern DNN detector (MTCNN, RetinaFace).

  2. Align

    Use the detected landmarks (eye centers, nose tip, mouth corners) to warp/rotate the cropped face into a canonical, frontal pose with the eyes horizontal — this removes pose, scale, and in-plane rotation variance before the network ever has to reason about identity.

  3. Embed

    Pass the aligned crop through an embedding network trained specifically to make same-identity faces land close together and different-identity faces land far apart in a fixed-length feature vector (e.g. 128-D or 512-D) — the actual "face representation" everything downstream operates on.

  4. Match

    Compare the new embedding against enrolled embeddings using a similarity measure (cosine similarity or Euclidean distance). For attendance, this is usually 1:N identification against the day's roster: the closest enrolled identity above a confidence threshold is marked present.

Research Enhanced

The embedding step above is exactly what FaceNet (Schroff, Kalenichenko & Philbin, CVPR 2015) popularized with its triplet loss: for an anchor face, a positive (same identity) and a negative (different identity), the loss directly pulls anchor-positive distance down and pushes anchor-negative distance up, rather than optimizing a classification objective. ArcFace (Deng et al., CVPR 2019) later improved on this with an additive angular margin loss operating directly on the angle between embeddings on a hypersphere, becoming one of the most widely deployed open-source face-recognition backbones.

Schroff, Kalenichenko, Philbin, "FaceNet", CVPR 2015 · Deng, Guo, Xue, Zafeiriou, "ArcFace", CVPR 2019

Exam Radar

Detection vs Recognition vs Verification — exam radar

  • Detection = "where" (box, no identity). Recognition/identification = "who, out of N" (1:N). Verification = "is it them" (1:1). These three words are not interchangeable on an exam.
  • Alignment always uses landmarks, not the raw box — that's exactly why a detector that also outputs landmarks (MTCNN, RetinaFace) saves you a separate alignment-network stage.
  • Common mistake: assuming "detection accuracy" tells you anything about recognition accuracy — a system can localize every face perfectly and still misidentify all of them.
02

Viola-Jones Algorithm (2001)

Optional Topic — Course Notes

Intuition first — the first real-time face detector

Paul Viola and Michael Jones (CVPR 2001) built the first face detector fast enough to run on 2001-era hardware — no GPUs, sub-GHz CPUs — by combining three separate ideas, each solving a different bottleneck: Haar-like features for cheap, interpretable local intensity cues; the integral image to compute those features in constant time; AdaBoost to automatically select the handful of features that actually matter; and an attentional cascade to avoid wasting compute on the overwhelming majority of image regions that obviously aren't faces.

Haar features — rectangle-based intensity differences

A Haar-like feature is simply the sum of pixel intensities under one rectangle minus the sum under an adjacent rectangle, at some position and scale inside the detection window (classically 24×24 pixels). The value encodes a coarse local-contrast pattern rather than raw pixel values — for example, an "eye region" feature subtracts a lighter rectangle (cheeks / bridge of the nose) from a darker one (the eye sockets above them), since eyes are reliably darker than the skin just below them across almost every face, lighting condition, and skin tone. A 24×24 window admits well over 100,000 possible Haar rectangles once you vary position, scale, and orientation — far too many to evaluate exhaustively at every location and scale in a full image without the next two ideas.

Integral image — turning an O(area) sum into an O(1) lookup
Definition: I(x,y) = Σ of all pixel intensities with x'≤x and y'≤y (above-and-left, inclusive) For any axis-aligned rectangle with corners A (top-left), B (top-right), C (bottom-left), D (bottom-right): Σ(rectangle) = I(D) − I(B) − I(C) + I(A) (A's contribution is subtracted twice — by B and by C — so it is added back once.) Cost: 4 array lookups + 3 add/subtract ops — independent of the rectangle's width or height. A single 24×24 window evaluates thousands of Haar features across all scales; O(1) sums are what makes this tractable.

AdaBoost — boosting a strong classifier out of weak features

Any single Haar feature, thresholded on its own, is a weak classifier — only slightly better than chance. AdaBoost (Adaptive Boosting) is a general boosting meta-algorithm that, over many rounds, picks the single best-performing weak classifier from the entire pool of candidate Haar features, re-weights the training examples so misclassified ones matter more in the next round, and combines all the chosen weak classifiers into one weighted-majority-vote strong classifier. Viola and Jones' key empirical finding: AdaBoost only needed to select roughly 200 Haar features out of the full candidate pool to build a classifier stage accurate enough to be useful — most of the ~100,000+ possible features turned out to be redundant or uninformative.

The attentional cascade — reject early, refine only what survives

In any real image scanned at every position and scale, the overwhelming majority of candidate windows contain no face at all. Running one expensive, fully-featured classifier on every single window would waste almost all of its computation on windows it should have dismissed instantly. The attentional cascade instead chains many classifier stages of increasing complexity: stage 1 uses just 1-2 Haar features and is tuned to reject a large fraction of obvious non-face windows immediately while still passing nearly every true face through (very high recall, low precision by design). Only the surviving windows are passed to stage 2 (a few more features, slightly more discriminating), and so on. A window must pass every stage to be declared a face; failing any single stage halts computation for that window right there. Because most windows die in the first stage or two, the average compute per window stays tiny even though the final stages are individually expensive — this asymmetry is exactly what enabled real-time detection on 2001 hardware.

Active Appearance Models — the classical alternative

Active Appearance Models (Cootes, Edwards & Taylor, 1998-2001) take a different classical approach, aimed less at "is there a face" and more at precise landmark localization and expression analysis. An AAM learns a joint statistical model (via PCA) of how a face's shape (a set of landmark coordinates) and texture (pixel appearance, warped into a mean reference shape) co-vary across a training population. Fitting the model to a new image is an iterative optimization that simultaneously estimates landmark positions and reconstructs an appearance — this made AAMs the workhorse predecessor to today's deep landmark regressors for facial landmark detection, expression recognition, and lip-reading.

Exam Radar

Viola-Jones — exam radar

  • Three ingredients, three separate jobs: Haar features (what to measure) + integral image (how to compute it in O(1)) + AdaBoost (which features to keep) + cascade (how to avoid wasting compute). Do not conflate AdaBoost with the cascade — AdaBoost selects features within a stage; the cascade arranges multiple boosted stages in sequence.
  • The integral image formula is a classic "compute one thing, reuse everywhere" trick — expect a direct numeric question giving you four corner values and asking for the rectangle sum.
  • Common mistake: thinking every stage of the cascade examines the same number of features. Early stages are deliberately cheap (1-2 features); later stages are progressively more expensive precisely because far fewer windows reach them.

DNN Face Detection Architectures

Optional Topic — Course Notes

The three names you need cold

ModelFunction
MTCNNThree cascaded CNNs: proposal, refinement, landmarks
RetinaFaceSingle-shot with extra landmark supervision; robust performance
FastFaceEdge-optimized detector for mobile/attendance systems

MTCNN — Multi-task Cascaded CNN, learned features replace Haar features

MTCNN (Zhang, Zhang, Li & Qiao, 2016) keeps the Viola-Jones "reject early, refine later" philosophy but replaces every hand-crafted piece with a learned one. Its three stages: P-Net (Proposal Network), a small fully-convolutional net that slides over an image pyramid to quickly generate candidate face windows with a first-pass bounding-box regression; R-Net (Refine Network), which takes P-Net's (still-noisy) candidates, filters out many more false positives, and tightens the boxes; and O-Net (Output Network), the final and most capable stage, which further refines the box and additionally regresses 5 facial landmarks (both eyes, nose tip, both mouth corners) — producing exactly the alignment input needed for the embed step in Section 01's pipeline, all within the detector itself.

RetinaFace — single-shot detection, landmarks as free auxiliary supervision

RetinaFace (Deng et al., CVPR 2020) drops the multi-stage cascade structure entirely and detects faces in a single forward pass, extending a RetinaNet-style single-shot detector. Its key idea: during training, add extra prediction heads for 5 facial landmarks (and, in its full variant, dense 3D face vertices) as auxiliary regression targets alongside the box. This multi-task supervision doesn't need to be used at inference if you don't want the landmarks — but training against it makes the shared backbone's features noticeably better, giving RetinaFace markedly more robust detection on small, occluded, and extreme-pose faces than a box-only detector of similar size, while also handing you box + landmarks together in one pass (no separate alignment network needed).

FastFace — trading a little accuracy for real-time, on-device speed

"FastFace"-style detectors target the deployment reality of attendance kiosks and mobile devices: a compact, edge-optimized architecture (following the same lightweight-backbone design principles as MobileNet-family networks), built to be pruning- and quantization-friendly so it runs at real-time frame rates on cheap fixed hardware — an embedded camera or phone SoC — rather than requiring a GPU server. This is the same overall speed-vs-accuracy trade-off you saw with YOLO versus the R-CNN family: a small accuracy cost buys a large, often necessary, latency and power win.

Research Enhanced

Notice the direct parallel to the two-stage-vs-one-stage story from object detection: MTCNN is architecturally a (learned) cascade, much like Viola-Jones was a (hand-crafted) cascade — both reject early and refine late. RetinaFace instead collapses everything into one pass, the same structural move YOLO made relative to R-CNN. The lesson generalizes across the whole field: staged rejection was originally a compute-budget necessity; once backbones and training signal are strong enough, a well-supervised single shot can match or beat a cascade.

Exam Radar

DNN detectors — exam radar

  • MTCNN's stage order is P-Net → R-Net → O-Net — proposal, then refine, then output+landmarks. Getting the order backwards is a classic wrong-answer trap.
  • RetinaFace's headline property is joint landmark supervision inside a single-shot detector — not "it's more accurate" in the abstract, but specifically more robust because the extra supervision improves the shared features.
  • Know WHY an edge-optimized detector (FastFace) exists at all: attendance kiosks and phones cannot assume GPU-class compute, so latency/power constraints, not raw accuracy, often drive the architecture choice.

Face Verification Metrics

Optional Topic — Course Notes

Detection quality still uses the metric you already know

Before you can verify or recognize a face, you first need to have detected it well — and the bar for "detected well" is the same one from the core Object Detection sessions: IoU-based detection with a standard TP threshold of IoU ≥ 0.5 between the predicted and ground-truth face box. Everything below this line assumes the box has already cleared that bar and is about scoring the identity decision on top of it.

TAR, FAR, FRR — the confusion-matrix of a yes/no identity decision
TAR (True Acceptance Rate) = genuine pairs correctly matched / total genuine pairs FAR (False Acceptance Rate) = impostor pairs incorrectly matched / total impostor pairs FRR (False Rejection Rate) = genuine pairs incorrectly rejected / total genuine pairs = 1 − TAR A "genuine pair" = two photos of the SAME person. An "impostor pair" = two photos of DIFFERENT people. Raising the similarity threshold needed to accept a match always trades TAR down against FAR down — you cannot improve both simultaneously without a genuinely better embedding model.

Why report "TAR @ FAR = X" instead of one accuracy number

Because every threshold choice trades TAR against FAR, an unconditional "accuracy" figure hides the operating point it was measured at. Different deployments tolerate wildly different false-acceptance risk: a phone's face-unlock can accept a slightly higher FAR for user convenience, while a banking authentication step authorizing a money transfer needs FAR pinned extremely low. The convention is therefore to fix FAR at a demanding value — commonly FAR = 10⁻³ for banking-grade systems — and report whatever TAR is achievable at that exact operating point, written as "TAR @ FAR = 10⁻³". Two systems should only ever be compared at the same FAR operating point; comparing a "TAR @ FAR=10⁻²" claim against a "TAR @ FAR=10⁻⁴" claim is comparing different problems.

Top-K identification rate — the 1:N counterpart

TAR/FAR/FRR describe a 1:1 verification decision. For 1:N identification, the system ranks every gallery identity by similarity to the probe, and Top-K identification rate is the fraction of probe queries for which the correct identity appears anywhere within the top K ranked candidates. K=1 ("rank-1 accuracy") is the strictest version; K=5 or K=10 is more forgiving and common when a human reviewer inspects a short candidate list rather than trusting the system's single top guess outright.

Exam Radar

Verification metrics — exam radar

  • FRR = 1 − TAR always — if you're given one, you can compute the other with no extra information.
  • "TAR @ FAR = 10⁻³" is a single number, but it is meaningless without stating the FAR it was measured at — always ask "at what operating point?" before comparing two systems' TAR figures.
  • Common mistake: treating Top-K identification rate and TAR@FAR as interchangeable — one describes a ranked 1:N search, the other a thresholded 1:1 decision.

Optical Character Recognition Pipeline

Optional Topic — Course Notes

Intuition first — OCR is detection, then classification, then cleanup

OCR mirrors the exact three-stage shape you've now seen twice: find the region, read the region, then fix likely mistakes using outside knowledge. The three stages are largely independent and swappable — you can pair a classical localizer with a transformer recognizer, or vice versa, depending on the deployment's document type and speed budget.

The three-stage pipeline

  1. Localisation

    Detect the bounding regions containing text (lines, words, or whole paragraphs) before any character is read. Approaches range from classical edge detection (fast, works on clean scanned documents with high contrast) to general-purpose YOLO-style object detectors repurposed to detect "text region" as a class, up to transformer-based document models like LayoutLM and DiT (Document Image Transformer), which jointly reason about text position and visual layout for complex real-world documents (invoices, forms, multi-column pages).

  2. Recognition

    Given a localized text region, predict the actual character sequence it contains. Classical engines like Tesseract and EasyOCR use a CNN+LSTM backbone trained with a CTC (Connectionist Temporal Classification) loss, which lets the network predict a variable-length character sequence without needing per-character segmentation labels during training. Newer systems instead use transformer decoders that attend over the image features to autoregressively predict the character sequence, similar in spirit to image captioning.

  3. Post-processing

    Raw recognizer output is corrected using outside structure: language models re-rank plausible full-word or full-sentence completions, lexicons snap a near-miss output to the closest valid dictionary word, and regex patterns validate or correct output against a known format (e.g. a license-plate pattern, a date format, an invoice-number template) — resolving ambiguous glyphs (0/O, 1/l/I, 5/S) that the recognizer alone cannot reliably disambiguate from pixels.

Research Enhanced

CTC (Graves, Fernández, Gomez & Schmidhuber, ICML 2006) is the piece that makes the CNN+LSTM recognition stage trainable at all without character-level segmentation: it sums over every possible alignment between the network's frame-by-frame character predictions and the target string (using a special "blank" symbol to absorb repeated or empty frames), so you only ever need the correct output string as a label, never the exact pixel boundary of each character. This is exactly why classical OCR engines could be trained on whole-word or whole-line image/text pairs rather than requiring laborious per-character bounding-box annotation.

Graves, Fernández, Gomez, Schmidhuber, "Connectionist Temporal Classification", ICML 2006

Exam Radar

OCR pipeline — exam radar

  • Localisation and recognition are separately swappable stages — never assume one specific architecture (e.g. "YOLO") is required; know which class of tool belongs to which stage.
  • Post-processing is not optional polish — it's where ambiguous glyphs (0/O, 1/l/I) that are genuinely unresolvable from pixels alone get fixed using language/lexicon/format context.
  • Common mistake: conflating CTC with a model architecture. CTC is a loss/alignment mechanism, not a network — it can sit on top of any frame-wise sequence output.

OCR Metrics — CER, WER & Localisation mAP

Optional Topic — Course Notes

Three metrics, three granularities

MetricDefinition
Character / Word AccuracyExact match at the specified granularity (character or whole word)
CER / WEREdit-distance formula: (substitutions + insertions + deletions) / length
mAP for localisationDetection accuracy of the text-region boxes, independent of recognition

mAP for localisation reuses exactly the same IoU-and-precision-recall machinery from the core detection sections — it measures ONLY whether the text-region boxes were found, saying nothing about whether the characters inside them were read correctly. A pipeline can have excellent localisation mAP and terrible CER (boxes found perfectly, characters misread), or the reverse (a slightly loose box that still lets the recognizer read the text fine).

Character / Word Error Rate — edit distance normalized by reference length
CER = (S + I + D) / N — S=substitutions, I=insertions, D=deletions, N=character count of the ground-truth reference WER = identical formula, computed on words instead of characters S, I, D come from the minimum-edit-distance (Levenshtein) alignment between the OCR output and the ground truth — the SAME alignment used to measure how many single-character edits turn one string into the other.

Worked example — GT "CAT", OCR output "COT"

  1. Align the strings character by character: position 1 C=C (match), position 2 A vs O (mismatch), position 3 T=T (match).

  2. The mismatch at position 2 is a single substitution: S=1. There are no insertions or deletions needed: I=0, D=0.

  3. Ground-truth length N = 3 characters.

  4. CER = (S+I+D)/N = (1+0+0)/3 = 1/3 ≈ 33%.

  5. Word accuracy requires an exact string match — "COT" ≠ "CAT", so the whole word is wrong regardless of how close it looks: word accuracy = 0.

AnswerCER ≈ 33% (one substitution out of three characters). Word accuracy = 0 — a single wrong character still fails an exact-match word-level check.

Exam Radar

OCR metrics — exam radar

  • CER's denominator is the GROUND-TRUTH length N, not the OCR output's length — a common numeric slip.
  • A low CER does not imply high word accuracy: one character wrong anywhere in a word still fails an exact-match word/field check (CAT/COT: CER≈33%, word accuracy=0).
  • Report CER/WER AND word/character accuracy together — for downstream systems needing exact values (invoice totals, plate numbers, account numbers), word accuracy is the number that actually matters operationally, even though CER is the more common training/benchmarking metric.

Conceptual Deep Dives

Compare & Contrast
Viola-Jones and MTCNN both use staged/cascaded designs — so what actually changed between 2001 and 2016?

  1. Viola-Jones' cascade rejects using hand-crafted Haar features, selected from a small fixed vocabulary of rectangle-difference templates by AdaBoost — the "features" themselves never change or learn.

  2. MTCNN's staged design (P-Net → R-Net → O-Net) keeps the "reject early, refine later" philosophy, but each stage is now a full learned CNN operating directly on raw pixels, so the features themselves are learned end-to-end and can jointly regress both boxes and landmarks — something no hand-crafted feature set could do without an entirely separate model.

  3. RetinaFace drops the staged/cascade structure entirely in favor of one single-shot network trained with rich auxiliary landmark supervision — proof that once the backbone and training signal are strong enough, explicit multi-stage rejection is no longer necessary for real-time speed.

Key Insight

Staged rejection was originally a compute-budget necessity for an era without GPUs. Deep single-shot detectors get their speed from raw model capacity and shared computation instead — the cascade idea didn't disappear, it got absorbed into a stronger backbone.

Why can't you report one unconditional "accuracy" number for a face-verification system?

  1. Verification is a threshold-based binary decision on a similarity score — every choice of threshold trades TAR against FAR; raise the threshold and FAR drops, but so does TAR.

  2. Different deployments tolerate different false-acceptance risk: unlocking a personal phone can tolerate a slightly higher FAR for convenience, while a banking system authorizing a transfer needs FAR pinned very low, so a "banking-grade" claim must first fix FAR (e.g. 10⁻³) and only then ask what TAR is achievable there.

  3. That's why the field reports paired "TAR @ FAR = X" operating points rather than one context-free accuracy figure — the same ROC-curve logic that underlies precision/recall trade-offs in ordinary object detection.

Key Insight

Any TAR number without a stated FAR (or vice versa) is close to meaningless — always ask "at what operating point?" before comparing two systems.

The CAT/COT example gives CER≈33% but word accuracy=0% — which one should you trust?

  1. CER is a fine-grained, partial-credit metric — it rewards getting most characters right even when the whole string isn't perfect, which is useful for gauging how "close" a recognizer is getting during development.

  2. Word accuracy is all-or-nothing at the word/field level — for downstream systems that must match a value exactly (an invoice total, a license plate, an account number), one wrong character is just as catastrophic as ten, so CER's partial credit can be misleadingly optimistic about deployment readiness.

  3. Reporting both separately lets you diagnose different failure modes: high CER with low word accuracy suggests the recognizer is far off; low CER with still-low word accuracy across many short fields (like plates) suggests small, individually minor character errors are quietly breaking every single field.

Key Insight

Pick the metric whose forgiveness profile matches how the output is actually used: per-character CER for benchmarking recognizer quality, per-word/per-field exact-match accuracy for deployment sign-off.

  • A0.93
  • BCannot be determined without knowing FAR
  • C0.07
  • D1.93
FRR = 1 − TAR = 1 − 0.93 = 0.07 — this relationship holds by definition at any single threshold, no FAR value needed. B wrongly assumes FRR depends on FAR (it doesn't — FRR only depends on TAR at the same threshold). A confuses FRR with TAR itself.Common mistakeBelieving you need the full ROC curve to get FRR from TAR — at a single fixed threshold, it's simple subtraction.
Q8HardCER worked example
Ground truth = "CAT", OCR output = "COT". What is the CER?
  • A0%
  • B≈33% (1 substitution / 3 characters)
  • C≈66%
  • D100%, since the word is entirely wrong
One substitution (A→O), zero insertions, zero deletions, ground-truth length 3: CER = (1+0+0)/3 ≈ 33%. C would require 2 errors. D confuses CER (character-level, partial credit) with word accuracy (all-or-nothing).Common mistakeReporting CER as if the whole word being "wrong" makes CER 100% — CER only counts actual character-level edits, not word-level correctness.
Q9HardWord accuracy
For the same "CAT" vs "COT" example, what is the word accuracy?
  • A67%
  • B33%
  • C0% — the entire word is wrong even though only one character differs
  • D100%
Word accuracy requires an EXACT string match; "COT" ≠ "CAT" regardless of how close the strings are character-by-character, so word accuracy = 0. A and B both wrongly try to apply CER's partial-credit logic to word accuracy.Common mistakeAssuming a low CER guarantees a nonzero word accuracy — they are unrelated once any single character differs.
Q10HardOCR metrics
Which metric evaluates ONLY the text-region localisation step, independent of whether the characters were read correctly?
  • ACER
  • BWER
  • CWord accuracy
  • DmAP for localisation
mAP for localisation reuses the IoU/precision-recall machinery from object detection to score only whether the text-region boxes were found — it says nothing about the recognized characters. Key Exam Takeaways

Exam Radar

Face Detection & OCR — five points to lock in before the exam

  • Viola-Jones combines three distinct mechanisms: the integral image (O(1) rectangle sums), AdaBoost (selecting ~200 useful Haar features out of a huge candidate pool), and the attentional cascade (rejecting most non-face windows in 1-2 cheap features per stage) — know which mechanism solves which bottleneck.
  • Modern face detectors are MTCNN and RetinaFace: MTCNN keeps a learned three-stage cascade (P-Net → R-Net → O-Net); RetinaFace collapses this into one single-shot pass with auxiliary landmark supervision. Verification is scored with TAR @ FAR operating points (e.g. TAR @ FAR=10⁻³ for banking-grade systems), never an unconditional accuracy number.
  • OCR always requires localisation before recognition — detect the text region first (edge detection, YOLO-style detectors, or transformer document models like LayoutLM/DiT), then read the characters inside it (CNN+LSTM+CTC or transformer decoders); the two stages are scored with entirely separate metrics.
  • CER quantifies errors via edit distance — CER = (substitutions+insertions+deletions)/N — and it is not the same signal as word accuracy: report BOTH character-level and word-level metrics, since a low CER (CAT/COT ≈ 33%) can still mean zero usable word accuracy for exact-match fields.
  • These are real deployed systems, not toy examples: attendance systems (detect→align→embed→match), banking/KYC verification (TAR@FAR operating points), license-plate reading, and invoice/document parsing (localisation + recognition + lexicon/regex post-processing) all directly apply the pipelines and metrics above.

01 Before the model ever sees data

Three buckets, one rule: never let them mix

Training, validation, and test data play three different jobs — confuse them, or let information leak between them, and your model's reported accuracy stops being true.

Model training — what, exactly, is happening

Training feeds a model data to learn from. Businesses lean on this because a model can process volumes of data no analyst could, surfacing patterns, anomalies, and correlations at scale. Two things decide whether that learning is any good: the quality of the training data and the choice of algorithm — this course deliberately stays on the data side of that pair.

// field note

Mechanically, training is the "fit" phase — gradient descent, splitting rules, whatever the algorithm's update rule is — minimizing a loss function step by step. But "garbage in, garbage out" dominates the outcome regardless of how good the algorithm is: early facial-recognition systems trained overwhelmingly on lighter-skinned faces produced measurably biased models even when the underlying algorithms were state of the art. That's the bridge between "ML" and "Data Management" — the framing here is data-centric, not algorithm-centric. (domino.ai/blog/what-is-machine-learning-model-training)

How to train a model — a repeatable process, not a one-off script

Treat it as a pipeline with a fixed order, not an ad-hoc sequence of notebook cells.

1 · Before training

Determine the problem statement, get access to the data, clean it. Skip the first step and you can build a technically excellent model that solves the wrong business problem.

2 · Configure

Choose the algorithm(s) and their hyperparameters — the knobs you set before learning starts, not learned from data.

3 · Split & prepare

Divide into train/test (and validation), then prepare the algorithm to actually run against those splits.

// why it maps onto CRISP-DM / TDSP

This is the same shape as CRISP-DM and Microsoft's Team Data Science Process: business understanding → data understanding → data preparation → modeling → evaluation → deployment. The point of naming it as a repeatable pipeline rather than a one-off script is exactly to stop teams from skipping "determine the problem statement" — the classic case of shipping a technically excellent model that answers a question nobody asked.

Data for three stages

The same dataset gets carved into three roles, each with a different contract with the model.

Training data

The model's DNA — what it continually evaluates itself against and adjusts on. This is where the actual learning happens.

Validation data

New, unevaluated information used during training to test behavior and tune hyperparameters — like practice quizzes while studying a textbook. They don't count toward the final grade, but they shape how you study.

Test data

Used only after training ends, to see how the model handles real, unseen data — like a final exam that was never used to tune anything along the way.

Train : Validation : Test ≈ 60% : 20% : 20% (or 70% : 15% : 15%)
// field note — the rule that gets broken most often

Data scientists pick the best-performing approach off these three splits, but bias, weak monitoring, and model opacity can all creep in unnoticed along the way. The classic cautionary tale is data leakage: early Kaggle contests were won by exploiting date-ordering or duplicate records that leaked from the test set into training — models looked excellent in evaluation and then failed in reality. The rule that prevents this: the test set must be touched only once, at the very end. Checking against it repeatedly and tweaking the model in response quietly turns it into a second validation set, and its reported performance stops being trustworthy. (domino.ai — model training, guide to cross-validation)

Split the dataset — why you can't train and test on the same rows

Training data is a limited resource that has to be allocated carefully — you cannot use the same rows to both train and test a model. Splitting into train/test sets is what lets you check for overfitting: great performance on training data, poor performance on anything new.

// field note — overfitting, the canonical failure

Overfitting is one of two canonical failure modes (the other is underfitting). The textbook example: a high-degree polynomial fit through noisy points passes through every single training point, wiggles wildly between them, and predicts terribly on new points. It's exactly why scikit-learn's train_test_split is one of the first functions taught in any ML course — and why Kaggle deliberately runs a "public" leaderboard test set alongside a hidden "private" one, specifically to stop competitors from overfitting to the visible test scores.

Cross-validation: don't just split once, rotate the split

10-fold cross-validation, worked step by step: (1) split the data into 10 equal folds, (2) designate one fold as the hold-out, (3) train on the other 9, (4) test on the hold-out fold, (5) repeat all of this 10 times, rotating which fold is held out each time. Averaging performance across all 10 hold-out rounds gives the cross-validated score — a single number that isn't at the mercy of one lucky (or unlucky) split.

Why bother rotating at all

A single 2-way train/test split can be "blunt": one fixed split may happen to ignore an important slice of the data, raising bias and overfitting risk. The fix is to split into k subsets, use k−1 of them to train and 1 to validate, repeat this k times rotating which subset is held out, and aggregate the results across all k trained models.

// field note — stratified k-fold and where this shows up in practice

k-fold is one of the most widely used evaluation techniques, built directly into scikit-learn as KFold and cross_val_score — the default choice when a dataset is too small to afford a separate, large validation set on its own. A critical special case is stratified k-fold, which preserves class proportions across every fold: essential for imbalanced problems like fraud detection, where positives are under 1% of the data and an unlucky ordinary split could hand an entire fold zero positive examples. k-fold is also the statistical backbone of GridSearchCV, which trains and validates once per hyperparameter combination, per fold. (domino.ai — guide to building models with cross-validation; GeeksforGeeks, k-fold cross-validation)

Two edge cases: LOOCV and LPOCV

Leave-One-Out CV (LOOCV) leaves exactly one observation out each round — the special case of k-fold where k equals the number of observations, n. It uses almost all the data on every training run, giving low bias, but it's slow: the model must be retrained n times. Leave-P-Out (LPOCV) leaves out a whole group of p observations at a time instead of just one; for n observations, each round trains on n−p, and the number of possible groups grows combinatorically as p grows.

// field note — cost and variance, not just accuracy

LOOCV is the k = n edge case of k-fold: each fold uses nearly the entire dataset, so the resulting performance estimate is almost unbiased — but it's computationally expensive and can show high variance between the n individual test scores. It's mostly reserved for small datasets where every data point is precious — small clinical studies, for instance — or for algorithms with a closed-form solution (like linear regression) where retraining is cheap. LPOCV is rarely used in practice at all: for n = 100 and p = 2, there are already 4,950 possible left-out pairs — a combinatorial explosion that makes it impractical outside toy problems. (Baeldung — cross-validation, k-fold vs. leave-one-out; GeeksforGeeks — cross-validation)

Shuffle splits — when you don't want to be tied to k

Leaving observations out one at a time is time-consuming. The alternative: generate a chosen number of splits — similar in spirit to k-fold — but shuffle the samples first, then split into train/test pairs, controlling randomness through a random seed.

// field note — Monte Carlo cross-validation

This is also known as "Monte Carlo cross-validation," and it's what scikit-learn's ShuffleSplit implements. Because samples are drawn independently each round, the same row can appear in the test set more than once — or never at all. It's useful precisely because it decouples two choices that k-fold ties together: you pick exactly how many train/test iterations to run (not fixed to k) and exactly what test proportion to use, independent of dataset size. That makes it a good fit for large datasets, where running full k-fold across every fold combination would be wasteful — a handful of smaller shuffled iterations gets you a reliable estimate for less compute. Variants include ShuffleSplit and StratifiedShuffleSplit. (scikit-learn.org/stable/modules/cross_validation.html)

02 Experimentation

ML Experimentation

Before a model reaches production it survives hundreds of small, deliberate trials — one knob turned at a time, every result logged — so the final choice is provable, not guessed.

What is an ML experiment?

A structured process of testing a model: it runs over a dataset, produces predictions, and those predictions are validated against known outputs. A single project can involve hundreds of experiments before one model is judged fit for production. Between runs only small changes are made — a parameter, a feature, a slice of data — and every change plus its result is tracked systematically, so the eventual model choice is a data-driven decision rather than a hunch.

Worked example — time-based splitting on a transfers dataset

Transfers recorded between 01/01/2016 and 05/01/2017 become the training and validation data; everything recorded after 05/01/2017 becomes the test set. In parallel, a hyperparameter search runs over the training data to find the optimum settings; model selection then weighs those settings against validation and test performance to pick the best model, which goes on to define a history window, a retrain frequency, and finally gets deployed.

// field note

Chronological splitting matters whenever data has a time axis — financial transactions, sensor streams, user behaviour logs. Shuffling such data before splitting lets future patterns leak into training, a classic form of data leakage that produces validation scores far rosier than real deployment performance. It's exactly why scikit-learn's TimeSeriesSplit forces validation/test folds to always sit chronologically after the training fold, and why fraud-detection and credit-scoring models are graded with "out-of-time" validation, not just out-of-sample. (Source: nebius.com/blog/posts/machine-learning-experiments)

Four experimentation approaches — change one knob at a time

Each approach holds everything constant except the one thing being tested, so any change in outcome can be attributed to a single cause.

ApproachFixedVariedExample
Model selection Dataset Model type Logistic regression vs. SVM vs. random forest vs. neural net on the same fraud dataset
Feature engineering Model Data features Scaling, log/sqrt transforms, polynomial features, or a filtered feature subset
Hyperparameter tuning Model, data Hyperparameters Learning rate, hidden-layer count, batch size via grid / random / Bayesian search
Data augmentation Model, labels Dataset (label-preserving) Random crop + horizontal flip + noise (AlexNet, 2012)

Approach #1 Model selection

Use a standardized or open-source dataset to trial different models — logistic regression, SVM, random forest, neural nets — over the same data, judged on consistent metrics (accuracy, precision, recall). To compare two candidates, either split one large dataset between them at random, or split by attribute: in fraud detection, credit-card transactions might route to one model and direct debits to another — a segmented, specialized-model-per-segment variant of the same idea.

Approach #2 Feature engineering

Transform raw data into features that better represent the underlying pattern, creating or reshaping features between experiments: scaling to a range, standardizing, log/sqrt transforms, or raising a feature to a power (polynomial features). Features can also be filtered between runs — trying different subsets to find the combination that performs best.

Approach #3 Hyperparameter tuning

Hyperparameters — learning rate, number of hidden layers, batch size — are set before training and never learned from data. Five search strategies:

  • Grid search — exhaustively tries every value in a predefined set. heavy
  • Random search — samples random values from a distribution. fast
  • Bayesian optimization — builds a probabilistic model of the loss surface to search intelligently. heavy
  • Hyperband — discards the worst 50% of configs after each round. fast
  • Genetic algorithms — evolves a population of configs, favoring high performers each generation.

Grid search and Bayesian optimization are the most thorough but computationally heaviest; random search and Hyperband are cheaper but can miss critical parameter regions.

grid search cost = valuesper paramnum params    e.g. 5 values × 5 hyperparameters = 5⁵ = 3,125 full training runs
// field note

That blow-up is grid search's "curse of dimensionality." Random search was popularized by Bergstra & Bengio's 2012 paper Random Search for Hyper-Parameter Optimization — it often finds near-optimal settings faster because usually only a few hyperparameters matter much, and grid search wastes trials on the unimportant ones. Bayesian tools like Hyperopt, Optuna, and Google Vizier are now standard in production, reaching good hyperparameters in far fewer iterations, while Hyperband and its successors ASHA/BOHB — widely used at scale in Ray Tune — cut wasted compute on bad configs early. (Source: keylabs.ai hyperparameter-tuning blog)

Approach #4 Data augmentation

Artificially grow the dataset's size and diversity by transforming examples without changing their label. For images: crop, flip horizontally, add noise before the next experiment — exposing the model to more views of the same concept.

// field note

The most famous historical case is AlexNet (Krizhevsky, Sutskever & Hinton, 2012) — the ImageNet-winning CNN that kicked off the deep learning boom. It took random 224×224 crops from 256×256 images plus horizontal flips, inflating the effective training set by roughly 2048×, and averaged predictions over multiple test-time crops (four corners + center, each with a flip). The authors called this augmentation "computationally free" since it ran on the CPU in parallel with GPU training on the previous batch. Modern successors: torchvision.transforms, albumentations for images; synonym replacement for text; SpecAugment for speech. (Sources: medium.com "AlexNet from scratch"; arxiv.org/html/2502.18691v1)

03 Proving the model isn't lying to you

Training accuracy is not proof of anything

Model validation is the discipline that decides whether a trained model can be trusted — not on the data it memorized, but on new data it has never seen. Skip it, and a model can look brilliant in training and fail catastrophically, expensively, and publicly in production.

Why validate at all

Model validation evaluates a model's performance and reliability before anyone acts on its output — checking accuracy, robustness, and generalizability against the real-world conditions it's meant to serve. The question it answers is narrow and unforgiving: can this model make accurate predictions on new, unseen data, not just the data it was trained on? Rigorous testing is how data scientists surface a model's flaws and weaknesses early enough to fix them. The most common mechanism for this is cross-validation — splitting data into training and validation sets so the model is graded on examples it never learned from.

Train on one set, judge on another

A model is fit on the training set, then evaluated on the validation set using metrics that quantify how well it classifies or predicts: accuracy, precision, recall, and F1 score. This step is what makes a model's output reliable and trustworthy rather than a guess dressed up as a number — it's how overfitting and underfitting get caught before deployment, and it's what lets a data scientist turn a model into an actionable, defensible recommendation instead of a liability.

Accuracy

Share of all predictions the model got right. Cheap to compute, easy to misread — see the field note below.

Precision

Of everything flagged positive, the fraction that actually was. The metric that matters when false positives are costly.

Recall

Of everything actually positive, the fraction the model caught. The metric that matters when false negatives are costly.

F1 Score

The harmonic mean of precision and recall — one number that punishes trading either off too far for the other.

Precision = TP / (TP + FP)  ·  Recall = TP / (TP + FN)  ·  F1 = 2·(Precision·Recall) / (Precision + Recall)
// field note

A textbook trap: a model that hits 99% accuracy detecting a rare disease can still be worthless. If the disease occurs in 1% of cases and the model simply predicts "no disease" for every patient, it scores 99% while catching zero real positives. Precision and recall expose this failure immediately; accuracy alone hides it completely.

The same trap catches rare-fraud detectors: a model that always predicts "not fraud" looks excellent on accuracy and is useless in production, because it never flags the fraud it was built to catch.

Where validated models earn their keep

Validation isn't an academic formality — it's the gate between a model and decisions that move money, treat patients, or run infrastructure.

Financial Institutions

Risk assessment, credit scoring, fraud detection, portfolio optimization — accurate predictions enable informed financial decisions.

Healthcare & Pharmaceuticals

Disease diagnosis, treatment prediction, drug development — validated models help predict patient outcomes and identify effective treatments.

Retail & E-commerce

Market forecasting, customer segmentation, recommendation systems — understand customer behavior, optimize pricing, sharpen personalized marketing.

Manufacturing & Supply Chain

Predicting equipment failure, optimizing production, improving supply chain management — enables proactive maintenance and reduces downtime.

Environmental Science

Predicting climate patterns, assessing environmental impacts, managing natural resources responsibly.

Energy & Utilities

Energy load forecasting, power grid optimization, renewable energy integration — maximizes efficiency, reduces cost, ensures reliable supply.

// when validation fails, it fails expensively

In finance, this isn't hypothetical: JPMorgan's 2012 "London Whale" incident produced over $6 billion in losses, partly traced to a flawed risk model — including a spreadsheet error in its calculations. The mispriced Gaussian-copula-based CDO models that helped trigger the 2008 financial crisis are the other case cited constantly in model-risk literature. Both are why bank regulators now mandate formal model validation by law, not by choice.

In healthcare, validated ML sits inside FDA-cleared diagnostic tools — for example, diabetic retinopathy detection from retinal images — only after extensive clinical validation, precisely because a wrong diagnosis is not a metric on a dashboard, it's a patient.

Six pillars of a model validation framework

A widely used "six-step model validation checklist" for AI credit-risk models — but general enough to apply anywhere a model makes a high-stakes decision. The first three pillars run before and during model-building; the last three run after it's deployed, plus who's accountable for all of it.

Pillars 1–3 — before the model ever sees production

1 · Conceptual Soundness

"Does this model make sense?" Every variable ties back to a business objective, assumptions are made explicit, and the method choice is backed by industry best practice — not just whatever performed best on a leaderboard.

2 · Data Quality

"Can we trust the training set?" Internal and third-party sources are both scrutinized for accuracy, completeness, and bias, with a log of how missing values and proxy variables were handled.

3 · Process Verification

"Was it built and deployed correctly?" Independent code review, reproducibility tests, and locked-down change controls confirm the model that was designed is the one actually running in production.

Pillars 4–6 — after deployment, and who answers for it

4 · Outcomes Analysis

"Does it perform — and stay fair?" Forecasting accuracy, stress and sensitivity tests, challenger-model benchmarking, and fair-lending disparity checks all run on live outcomes, not training-time metrics.

5 · Ongoing Monitoring

"Is the model still healthy?" Drift thresholds and alerts, plus a periodic review of whether the population the model now sees still matches the one it was built for after market or product shifts.

6 · Governance

"Who's accountable end-to-end?" Clear roles, access rights, and a defined redevelopment horizon — every decision about the model is traceable and auditable, not tribal knowledge.

// SR 11-7 — where this checklist actually comes from

This six-pillar structure closely mirrors the U.S. Federal Reserve's SR 11-7, "Supervisory Guidance on Model Risk Management" (issued jointly with the OCC in 2011) — the foundational U.S. banking regulation on model risk. It rests on three pillars: robust model development, effective validation (conceptual soundness, outcomes analysis, ongoing monitoring), and strong governance.

SR 11-7 exists because of catastrophic model failures, not theory: the 2008 financial crisis, JPMorgan's 2012 London Whale ($6B+ loss), and Knight Capital's 2012 trading-algorithm glitch — roughly $460 million lost in 45 minutes from a badly deployed and unmonitored piece of trading software. Today, SR 11-7-style frameworks are being adapted well beyond banking into "AI governance" broadly — fairness and bias checks on any high-stakes ML system, from credit to hiring to healthcare.

04 Data about data

You've already seen metadata a thousand times

Right-click any file, check "Properties," and you're staring at metadata — you just never called it that. This section names the thing, sorts it into a taxonomy, and explains why entire tooling categories (data catalogs, governance frameworks) exist to manage it at scale.

Have you seen these?

Two Windows Explorer screens almost everyone has opened without a second thought — neither one shows you the file's actual content.

Properties → Details tab

Right-click a Word document, hit Properties, open Details: Title, Authors, Last saved by, Revision number, Program name, Content created, Date last saved, Total editing time. Not one word of the document itself — just facts about how it came to exist.

Explorer's "Choose Details" column picker

Right-click a column header in any file list and a menu of dozens of optional columns appears: Bit depth, Bit rate, Broadcast date, Business address, Business phone, Date modified, Type, Size... a checklist of attributes about files, sitting one right-click away on every machine you've ever used.

// the point

Metadata is data about the file, not the file's content — who made it, when, with what program, how big it is. Everyone has seen it. Almost nobody thought of it as a formal concept worth naming, until it needs to be searched, governed, or trusted at scale.

More examples: the data / metadata split, four ways

The same divide repeats across completely different kinds of objects — the content is the "data," everything describing that content is the "metadata."

A cat photo

Data the actual pixels.
Metadata EXIF fields: Filename, Author, Date, dimensions/size, Camera model, Lens, Aperture, Exposure, Flash, and — often — embedded GPS coordinates of where it was taken.

A book

Data the body-text pages themselves.
Metadata the Summary and Table of Contents — a compressed description of what's inside, without being the inside.

An email

Data the message body.
Metadata its Properties dialog: importance, sensitivity, encryption, delivery/read receipts, tracking — none of it the message, all of it about the message.

A database table

Data the rows: employee_id, first_name, last_name, nin, department_id.
Metadata the schema / data dictionary — a separate table of Column, Data Type, Description for that same table.

// field note

EXIF GPS metadata has real teeth: journalists and open-source investigators routinely geolocate events by pulling embedded coordinates straight out of photos, while photographers and activists are separately warned to strip EXIF before publishing to avoid revealing exactly where they were standing. And the "schema / data dictionary" example is the entire premise of a data catalog — tools like Alation, Collibra, Amundsen, and DataHub exist to scan databases automatically and auto-generate this "metadata about columns" across thousands of tables, at a scale no human could document by hand.

Why do we need these details?

Metadata isn't collected for its own sake — each dimension above solves a specific, recurring organizational problem.

Empowers data discovery

A strong metadata layer works like a search engine for enterprise data — finding a relevant dataset without relying on tribal knowledge or a lucky Slack thread to the one person who remembers where it lives.

Boosts data literacy & democratization

Bridges data producers (engineers) and data consumers (business users) with a common, documented language, instead of each side guessing what a column actually means.

Enables trust and compliance

In regulated industries — finance, healthcare, pharma — knowing exactly who touched what data, and when, is non-negotiable, not a nice-to-have.

Accelerates cloud modernization

Cloud migrations rarely stall on compute — they stall because nobody can say with confidence which data is safe to move, delete, or refactor. Metadata is what supplies that confidence.

// field note

The "tribal knowledge" problem directly drove the rise of modern data-catalog tooling from the mid-2010s on: LinkedIn's internal tool WhereHows evolved into the open-source DataHub; Lyft built Amundsen; Airbnb built Dataportal — all because engineers were burning large fractions of their time just figuring out what data existed and whether it could be trusted. And it isn't only a productivity story: GDPR and HIPAA legally mandate exactly this "who touched what data and when" traceability, turning metadata management from a nice-to-have into a compliance requirement.

Dimensions of metadata

One useful lens: the who/what/when/where/why of journalism, applied to a dataset instead of a news story. Five angles, one central subject.

Types of metadata

The dimensions above are informal angles of inquiry; the data-management literature formalizes them into five named categories, each answering a different operational question.

TypePurposeExamples

StructuralDescribes organization and relationships within/between dataDocument sections, table schemas, primary/foreign keys
AdministrativeManages access, permissions, complianceAccess rights, creation/modification dates, copyright, file type

Descriptive → helps you find it

Functions like a library catalog card: title, author, keywords, summary — enough to locate the thing without opening it.

Structural → how the pieces relate

A table of contents for a document, or primary/foreign keys for a database — the map between parts, not the parts themselves.

Administrative → who can do what

Access rights, copyright, retention dates — the governance layer that decides who's allowed to touch it.

Technical → the nuts and bolts to open it

Format, resolution, compression, encryption — the specs a program needs before it can even render the file.

// field note

This five-type taxonomy closely parallels classification schemes from library/information-science standards bodies like NISO and governance frameworks such as DAMA-DMBOK (the reference text for data-governance professionals). In practice, technical metadata is exactly what makes formats like Parquet and ORC "self-describing" — schema and compression info travel embedded inside the file itself — while structural metadata (foreign keys, schemas) is precisely what modern data catalogs like DataHub, Amundsen, and Collibra automatically extract by scanning a company's databases and warehouses. Statistical metadata is the one most often skipped — and the one that makes a result reproducible months later.

05 Metadata Categories for ML Data

ML Metadata Categories

Beyond a plain experiment log, ML systems accumulate six distinct flavors of metadata — about the artifacts they pass around, the datasets and features and labels that feed them, the models that come out, and the pipelines that wire it all together. Each answers a different question when something breaks.

Metadata is not one bucket. A dataset's provenance, a feature's legal status, a label's confidence, and a model's git SHA are logged by different people, at different times, for different reasons. The table below is the map — six categories, each with its own core question — before the detail sections unpack the fields inside each one.

CategoryCore question it answers
Artifact metadataWhat exactly is this file, and how do I know it hasn't silently changed?
Dataset metadataWhere did this data come from, and am I allowed to use it?
Feature metadataWhat does this feature actually compute — and is it even legal to use here?
Label metadataHow trustworthy is this label, and against which label set was a model scored?
Model metadataHow was this version built, and how has it performed — then and now?
Pipeline metadataWhat already ran in this DAG, and where can it safely resume from?

Artifact Metadata

On top of experiments and training runs, ML projects generate artifacts — inputs and outputs that get reused across many runs and versioned over time: datasets, trained models, prediction files, any file-like object worth tracking. It generalizes the software-engineering "build artifact" (a compiled binary) into ML, where the "build" is a training run.

Reference

Path to the dataset or model — an S3 bucket key, a filesystem path, anything that resolves to the actual bytes.

Version

An md5 hash of the dataset or model, so two versions can be diffed at a glance without re-downloading either.

Preview

A dataset or prediction preview — a table head, an image-folder snapshot — to sanity-check content without opening the whole artifact.

Description

Extra context, e.g. the column names for a tabular dataset artifact.

Authors

Who created or modified this artifact, and when.

// field note

These fields are drawn almost verbatim from Neptune.ai and Weights & Biases. W&B's wandb.Artifact versions datasets and models by content hash and draws a lineage graph showing exactly which run produced and which run consumed each artifact.

Dataset Metadata

Think of dataset metadata as a birth certificate for the data — where it came from, who is responsible for it, and what you're allowed to do with it.

Dataset provenance

A lookup table of logs from source systems, a key plus download date for an external provider, or a reference to the code that generated it.

Dataset location

Where the unprocessed, raw dataset lives. For ongoing data like system logs, a reference to the log store or datastore instead.

Responsible person / team

Who chose to download or create it, or who owns the system that produces it.

Creation / version date

The first date a dataset version was used — the anchor point for every downstream comparison.

Use restrictions

Licensing or governance restrictions, documented so a compliance review doesn't have to be reconstructed from memory.

// field note

Closely echoes the 2018 "Datasheets for Datasets" paper (Gebru et al.), modeled on hardware-component datasheets: motivation, composition, collection process, and legal/ethical considerations documented before release. Since adopted by Google (Data Cards), Hugging Face (Dataset Cards), and academic conferences that now require datasheet-style documentation at submission.

Feature Metadata

A feature is code plus a definition, and both drift. Without a version and an owner attached, "why did this feature change last Tuesday" becomes unanswerable.

Feature definition version

Reference to the code or description of what data the feature reads and how it's processed. Update on every change; versioning and restricting which versions are in use keeps the codebase predictable and maintainable.

Responsible person / team

Authorship and maintainer info — who to ask when the feature is suspected of causing a regression.

Creation / current version date

Change history for the feature definition over time.

Use restrictions can be illegal

Trickier to store than the others — some features may be illegal to use in certain jurisdictions or contexts, not merely undesirable.

// field note

This is exactly the problem feature stores exist to solve. Uber Michelangelo Palette hosts 20,000+ versioned, documented, reusable features behind a searchable "Gallery," so new model teams reuse vetted features instead of re-deriving them. Feast and Tecton were built to solve the same metadata sprawl at scale. The legal-restriction point ties to fair-lending law — the U.S. Equal Credit Opportunity Act restricts protected-class-correlated features in credit models.

Label Metadata

Label quality caps how good a model can ever be — no amount of architecture tuning fixes a mislabeled training set.

Label definition version

Which labeling instructions produced this set of labels.

Label set version

Labels get corrected and new labels get added over time. Comparing against an older model may require the older label version, for a fair apples-to-apples comparison.

Label source

License source, the human annotator plus any QA applied, or the algorithm if the label was auto-generated.

Label confidence

Different confidence estimates per label depending on how it was produced — e.g. lower confidence for automated or newer-annotator labels — so users can choose thresholds for which labels to trust in training.

// field note

Ties to the shift from "model-centric AI" to "data-centric AI," a term popularized by Andrew Ng around 2021 — for many mature architectures, improving label and data quality yields bigger gains than tweaking the model. Weak-supervision frameworks like Snorkel (Stanford) programmatically combine multiple noisy weak labeling sources into probabilistic, confidence-weighted labels instead of treating every label as equally certain — precisely this slide's "label confidence" idea.

Model Metadata

Content logged for a model version: training parameters, evaluation metrics, prediction examples, dataset versions, testing-pipeline outputs, references to the weights files. As the source material puts it: when your models touch users or help clients make decisions, you'd better know a lot about them.

// field note

Drift has well-defined flavors: data drift (input feature distributions change — e.g. customer age distribution shifts), concept drift (the input–output relationship itself changes — e.g. what counts as "fraud" evolves as fraudsters adapt), and performance drift (the observed downstream effect — accuracy or precision degrading). Drift detection is now its own product category (Evidently AI, Arize, WhyLabs, Fiddler) and is required by SR 11-7's "Ongoing Monitoring" pillar. The canonical cautionary tale: Google Flu Trends predicted flu outbreaks from search queries, drifted badly as search behavior changed, ended up overestimating flu prevalence by more than double, and was discontinued.

Pipeline Metadata

ML models are increasingly trained inside automatically-triggered pipelines — triggered when performance drops below a threshold, when new labeled data arrives, when a feature branch merges to develop, or simply on a weekly schedule. It's usually a CI/CD workflow wired to an orchestration tool (Airflow, Kubeflow, Kedro). Every trigger starts a computation DAG (directed acyclic graph), and every node in that graph produces its own metadata.

This metadata serves a different purpose than experiment or model metadata: it isn't there to explain a model to a human, it's there to compute the DAG efficiently.

Input and output steps

What goes into and out of each node, and whether all of a node's input steps have completed before it can run.

Cached outputs

References to intermediate results and artifacts, recording which run produced them and where the binaries live — so computation can resume from a certain point in the graph instead of restarting from scratch.

// field note

Some ML training systems produce this metadata automatically — ML Metadata (MLMD), Google's open-source library built for and bundled with TensorFlow Extended (TFX), records every artifact, every execution, and the full lineage graph connecting them (backed by SQLite or MySQL), letting engineers answer lineage questions like "what data trained this exact production model?" Kubeflow Pipelines adopted google/ml-metadata as its own backend too, making it a shared standard beyond TensorFlow. DAG orchestration itself (Airflow, Kubeflow, Kedro, Dagster) borrows from earlier ETL tooling, but ML pipelines add lineage tracking at every node, not just task success or failure. Such systems are either designed in from day one, or somewhat difficult to implement later.

06 Tracking what you did, and where to look it up

Metadata systems, and the store that holds them together

One vs. many systems, build vs. buy, and the repository/registry/store vocabulary that decides whether a pipeline or a model gets to be the star of the show.

Metadata systems — introduction

A metadata system tracks what you're doing. For features and labels alone, it should minimally track feature definitions and which versions of them are used in which model definitions and trained models. Two common failure modes recur across orgs: the most common mistake is building ML infrastructure with no metadata system at all, and regretting it later once nobody can answer "which features fed this model?"; the next most common is building several scattered metadata systems, each bolted on to solve one narrow problem in isolation.

Approach — what needs tracking

A workable approach needs systems covering: feature definitions and their mapping to feature stores; label metadata — the spec, plus when labels were applied to which feature values; the mapping from model definitions to trained models, and the engineers/teams responsible for each; and trained model versions, including when each was put into production. Quality and fairness evaluation systems need to read from all of these to trace the contributing cause of a quality regression or a fairness violation back to its source. That leaves one central architectural choice.

One System

Advantage: simple to correlate across subsystems — one place simplifies analysis and reporting.

Drawbacks: the schema is hard to get right upfront, so columns keep getting bolted on as new tracking needs surface, forcing backfills of existing data; it's hard to keep stable and reliable. Metadata systems should never sit in the live training/serving path, but it's hard to imagine feature engineering or labeling continuing if the metadata system that tracks them goes down — so an outage still hurts the humans doing that work.

Multiple Systems

Advantage: standard decoupling benefits — one for features/labels, one for training, one for serving, one for quality monitoring, each developed independently, nimbler to modify or extend; an outage in one has limited blast radius on the others.

Drawbacks: harder analysis and reporting — you need a process that joins data across the features/labeling/training/serving systems, and the systems must be designed to allow that: shared unique identifiers, or a separate system that tracks relationships between the metadata systems.

// field note

This is a direct instance of the classic monolith vs. microservices debate, applied to ML metadata. Many real orgs land on a hybrid: a central metadata store or registry — MLMD, or an internal system — whose only job is tracking relationships (shared IDs) across otherwise-decoupled subsystems, exactly the fix the Multiple Systems column proposes. The same "store as superset of registry" idea reappears below.

Setting up a metadata system — build, opensource, or buy

An old software dilemma. Before choosing: understand what problem you're actually solving; check whether a tool already solves it before building one; assess how much time it will really take to build, maintain, and customize; and don't underestimate the effort involved — this recurs almost identically later for model registries.

ML metadata store — introduction

The metadata store is a centralized place managing all metadata about experiments — experiment logs, artifacts, models, pipelines. It holds metadata about ML artifacts, not the artifacts themselves, and it comes with a UI for reading and writing model-related metadata: "anything you need for any/every ML model you build and deploy." It lets you log, store, display, monitor, compare, organize, filter, and query all model-related metadata from one place.

All three are, at bottom, databases for metadata — the difference is functional, in what they're used for and how deliberately curated their contents are.

Pipeline-first vs. model-first metadata stores

As ML orgs mature, training happens inside automated, orchestrated pipelines — running an experiment, a training job, or a retraining job is always tied to executing a pipeline. That leaves two design philosophies for what the metadata store treats as the first-class object.

Pipeline-first

Treats pipelines as first-class objects, and associates the resulting models and experiments with them. If your focus is the process, get something like MLMD — the metadata layer powering Kubeflow and TFX, built around Artifacts, Executions, and Contexts inside a DAG-oriented pipeline.

Model-first

Treats models/experiments as first-class objects, and treats pipelines as just a mode of execution. If your focus is the output, get something like MLflow or Neptune — built around Experiments containing Runs, with any pipeline (e.g. Airflow) orchestrated externally and only called into for logging.

// field note

Orgs already committed to Kubeflow/TFX keep using MLMD, since its data model already mirrors their pipeline DAGs. Orgs that value flexible comparison across ad-hoc training approaches — many small experiments, not one fixed pipeline shape — prefer the MLflow/Neptune/W&B style of tool instead.

07 Provenance, not just definitions

Metadata Management & Lineage Tracking

A dataset's schema tells you its shape. Metadata management and data lineage tell you where it came from, who touched it, and what happened to it in between — the part of governance that turns "trust me" into "trace it."

Metadata management, precisely

Metadata management is the discipline of capturing, organizing, and maintaining metadata — the practice built on top of the metadata types already covered as a taxonomy. Restated here as the three things a management system actively works to keep current:

Structural

Describes how data is organized — the relationships between datasets and their elements (tables to columns, files to schemas, parent to child).

Descriptive

Information about individual data instances, letting a user identify one specific item inside a much larger dataset.

Administrative

The technical detail needed to manage a resource: when and how it was created, and who is permitted to access it.

Data lineage, precisely

Data lineage is a companion data-governance concept: it supplies the origins of a dataset, how it has moved over time, and what happened to it between initial creation and its present state. Three angles on the same underlying map:

Forward

How data moves from source toward destination — downstream. Answers "if I change this source table, what breaks further down the pipeline?"

Backward

Reveals the origin of data — upstream. Answers "this number looks wrong — where did it come from, and what transformed it along the way?"

Horizontal

The flow of data across systems and processes — the broader cross-system map that forward and backward lineage are both slices of.

How the two relate

Data lineage is not a separate governance activity bolted on beside metadata management — it is a part of it, specifically an essential element of descriptive metadata, since it provides information about a dataset's history. What gets captured typically includes who accessed the data, what changes were made, when, and why. A robust metadata management system is what makes lineage maintainable and understandable at all — giving a clear view of where data comes from, how it relates to other data, how it's used, and how it changes over time.

The synergy: what lineage adds once it's inside metadata management

Understanding transformation

See exactly what each step did to the data on its way from source to destination.

Tracking usage

Know which reports, models, and downstream tables actually consume a given dataset.

Debugging

Trace a wrong number back through every transformation to the exact point it broke.

Impact analysis

Before changing a source table, see everything downstream that would be affected.

Governance & compliance

Demonstrate, on demand, exactly how a reported figure was produced and by what path.

Lineage is a specific type of metadata, not a competing discipline — the table below draws the line cleanly.

// field note

This isn't only good engineering hygiene — it's law for large banks. BCBS 239, the Basel Committee's risk-data-aggregation principles issued after the 2008 financial crisis, explicitly requires institutions to trace the full lineage of any number in a risk report back to its source systems. Lineage tracking there is a hard regulatory requirement, not an optional nicety.

Modern tooling has converged on column-level lineage as the standard, not table-level: tracing not just "table A feeds table B" but "this exact column was derived from these exact upstream columns via this exact transformation." dbt exposes this natively through its model DAG; catalogs like Atlan and Collibra, and the open OpenLineage/Marquez standard, consume it to power searchable, org-wide lineage graphs.

08 Module 08

ML Experiment Tracking

Every model you ship is the survivor of dozens of runs you probably can't fully reconstruct. This module is about closing that gap — from the ad-hoc pain point, to what experiment tracking actually captures, to how teams implement it at different scales.

// a familiar complaint

"So far, we have been doing everything manually and sort of ad hoc. Some people are using it, some people are using that, it's all over the place. We don't have anything standardized. But we run many projects, the team is growing, and we are scaling pretty fast. So we run into a lot of problems. How was the model trained? On what data? What parameters did we use for different versions? How can we reproduce them? We just feel the need to control our experiments…"

— an unfortunate Data Scientist, describing a team that scaled faster than its process.

Why? — experiments multiply faster than you can track them

Developing an ML model means running a lot of experiments, and any one of them may differ from the last in ways that are easy to lose track of: a different model or hyperparameter set, a different training/eval split, a small one-off tweak to the code, or even the same code running in a different environment — an unnoticed PyTorch or TensorFlow version bump is enough. Each of these produces a different set of evaluation metrics, and keeping it all straight gets hard, fast — especially once you're trying to organize and compare dozens of runs and still feel confident about which one is actually best.

Some experiments announce themselves early — you can tell almost right away they won't beat your current best. The right move is to stop them before they burn days or weeks of compute, not let them run to completion out of habit. Recognizing that moment, and having the discipline to act on it, is only possible if you're tracking runs in the first place. That's the gap experiment tracking fills.

What? — everything about a run worth remembering

Experiment tracking is the process of saving every piece of information you care about, for every single run, so that the question "how was this model trained?" always has an answer. In practice, that metadata includes:

Code & environment

Training/eval scripts and environment config files used for the run.

Data

Training and evaluation data — statistics and versions, not just a folder name.

Configuration

Model architecture and training parameter configs for that specific run.

Metrics

ML evaluation metrics on train, validation, and test.

Model weights

The actual trained artifact, tied back to the run that produced it.

Visual diagnostics

Confusion matrices, ROC curves, and example validation predictions (especially common in computer vision).

Components of an experiment tracking system

Structurally, an experiment tracker is nothing more than a specialized ML metadata store: client libraries feed a central database, and a dashboard sits on top for humans to browse.

Experiment database

Stores the experiment metadata itself — the thing that gets logged to and queried from.

Experiment dashboard

The visual interface for browsing, filtering, and comparing what's in the database.

Client library

Code-level methods for logging and querying — e.g. mlflow.log_metric(...) — called from inside training scripts.

Experiment tracking vs. model management vs. MLOps

Experiment tracking is a specialized, focused sub-discipline of MLOps: it lives in the iterative development loop — architecture, training, evaluation, repeat — where you're trying many things to hit a target performance. Model management is the layer around it that begins once models are ready to leave that loop. MLOps is the outer layer that carries a model all the way from data to a monitored production system.

Model management starts once models are ready to go to production: it streamlines the move from experimentation to production, helps with versioning, organizes artifacts in a model registry, lets you test multiple versions in production side by side, and lets you roll back to an older version if a new one misbehaves. Not every model reaches that stage — but experiment tracking is still worth doing even if it never does. That's especially true for research-focused projects, where the point may never be a deployed model at all, and the metadata itself is the valuable output: it gives real insight into what worked, what didn't, and why, and it means you're ready the moment a "magical" result does show up.

Benefits

One source of truth

Every experiment and model, organized in one place — regardless of where it ran.

Automated process

Compare runs, analyze results, and debug training with almost no extra manual work.

Better collaboration

See what everyone on the team is doing, share results, pull data programmatically.

Live monitoring

Watch runs live and manage experiments from anywhere, at any time.

One source of truth, in practice

Training runs happen everywhere — a personal laptop, a work PC, a dedicated cloud instance, a university cluster, a Kaggle kernel, Google Colab. Sometimes it's a quick test in a notebook; sometimes it's a distributed hyperparameter-tuning job spread across a fleet of machines. Over the life of a project — especially with more than one person on it — results end up scattered across all of those places. An experiment tracking system is built to log everything to one experiment repository regardless of where the run happened, which makes the whole project far easier to manage than chasing results across machines and notebooks.

What centralization actually buys you

Once everything lands in one repository, a lot of previously tedious work becomes close to free:

Find and reconstruct

Search and filter experiments quickly; drill into exactly what was tried — code, data version, architecture; reproduce or re-run a past experiment on demand; pull metadata even if the machine that ran it (a terminated spot instance, say) is long gone.

Compare, without extra work

Compare metrics and parameters across runs; overlay learning curves; group and compare by data version or parameter value; line up confusion matrices, ROC curves, and other performance charts side by side.

Inspect what the model is doing

Compare best- and worst-case predictions on test/validation sets; view code or notebook diffs for model, feature-engineering, and training logic; check hardware consumption per run; inspect prediction explanations via SHAP or LIME.

...and anything else

Compare rich-format artifacts like video and audio, and — in short — compare anything else you bothered to log.

What to track — code and environment

Code

Preprocessing, training, and evaluation scripts; feature-engineering notebooks; utility code — everything needed to run, or re-run, the experiment.

Environment

The easiest path is saving config files: Dockerfile, requirements.txt (pip), pyproject.toml (hatch/poetry), conda.yml (conda). You can push built Docker images to a registry instead, but plain config files are usually easier to save and diff.

What to track — data, parameters, metrics

Data

Save data versions — a hash or an immutable resource location — so it's always clear what actually trained the model. Tools like DVC version datasets and can save their .dvc files straight into your tracking tool.

Parameters

Crucial to log for every run. Be careful with command-line parameters (argparse, click, Hydra) in particular — it's a very easy place to silently lose tracking discipline. ("I have some horror stories to share.")

Metrics

Log evaluation metrics on train, validation, and test for every single run — not just the ones that looked promising.

// closing the gap A run launched as python train.py lr=0.01 is easy to under-document. Hydra exists specifically to auto-log the fully resolved configuration for every run, so the command line stops being the weak link.

Implementation — choosing an approach

ML projects vary a lot in shape and size, so there's no single right way to track experiments. What fits depends on:

  • Team size
  • Number of experiments planned
  • Model complexity
  • Level of metadata detail required
  • Key project/research goals — improving specific capabilities vs. squeezing out raw performance

Three common approaches show up in practice, roughly in order of how much a team has outgrown the last one: manual tracking with spreadsheets and naming conventions, software versioning tools like Git, and automated tracking with dedicated experiment-tracking tools.

How: spreadsheets to log details by hand, plus systematic naming conventions for files and directories — model version, learning rate, batch size, headline result, all baked into the filename.

Easy to implement — no tooling to install. Fine for small or personal projects run out of Excel or Google Sheets.

Cons

Falls apart at scale: real risk of logging the wrong info or overwriting someone else's row. Manually enforcing naming conventions across a team is time-consuming and error-prone.

Software versioning tools — bending Git into an experiment tracker

The next step up is versioning experiment metadata in GitHub directly — committing metrics, parameters, and charts via a post-commit hook once a run finishes. It works, for a while. As one practitioner put it: "GitHub wasn't built for machine learning."

  • Git's compare tooling is built for two branches (master vs. develop) — comparing three or more experiments, or overlaying learning curves, doesn't work well.
  • Organizing many experiments becomes difficult or impossible — a branch-per-idea or branch-per-experiment scheme gets unusable fast.
  • No live monitoring — information is only saved once a run finishes and gets committed.

Automated tracking — tools built for this job

Instead of stretching a general-purpose tool to fit, automated tracking uses solutions built specifically for tracking, organizing, and comparing ML experiments: logged to a central experiment database, displayed in a dashboard, searchable, comparable, and drillable by design. Purpose-built tools are consistently easier for ML people to use than general tools, integrate more naturally with the ML ecosystem, and ship with experiment-focused features general tools never will.

09 ML Experiment Tracking Frameworks

Six Ways to Stop Losing Track of Your Runs

Organizations rely on specialized experiment-tracking software to record, organize, and compare data from ML experiments. These tools are built for ML, deep learning, and LLM workflows alike, and integrate seamlessly with the frameworks and platforms teams already use.

Why a dedicated tool at all

Once a project runs more than a handful of experiments, spreadsheets and folder names stop working. A run needs its hyperparameters, metrics, code version, environment, and output artifacts captured together and made comparable — that's the job these frameworks exist to do.

MLflow open-source

Logs hyperparameters, metrics, and output artifacts, and stores the full run history — data versioning, code snapshots, environment details. Runs are compared through a simple UI to surface the best-performing model. A model registry versions models and moves them through stages such as staging → production, so only the vetted model reaches production.

Comet SaaS

Cloud-based platform for tracking, comparing, and managing experiments with real-time logging — metrics, hyperparameters, and performance are visible as training progresses. Multiple experiments are compared in one UI, with visualizations of metric trends and confusion matrices. Git integration captures a code snapshot per experiment for reproducibility.

Weights & Biases SaaS

Integrates with popular ML frameworks without disrupting existing workflows, with the same real-time logging as Comet plus a wide range of visualizations for comparing experiments and plotting results. Its signature feature is hyperparameter sweeps — automated exploration of parameter combinations — alongside automatic tracking of code and datasets per run.

Neptune SaaS

A web-based, user-friendly platform for experiment tracking and model management. A centralized repository holds experiments, metrics, models, and logs for transparent search and retrieval. Its flexible API supports a nested metadata structure you design yourself, plus custom dashboards mixing resource usage, learning curves, and confusion matrices in one view.

DVC Git-native

Data Version Control — open-source version control for data, models, and pipelines, not just code. It integrates tightly with Git and uses a DAG-based approach to track changes to datasets, params, and code. Pipelines are defined as stages (preprocessing, training, evaluation) and back onto S3, GCS, Azure Blob, or local storage.

DagsHub Git-native

Built on top of MLflow, DVC, and Git rather than replacing them, avoiding vendor lock-in. Delivers a GitHub-like experience for ML projects — a visual interface for every experiment and a lineage tracking system that traces any result back to the exact version of data and code that produced it.

10 From "whose laptop is the model on" to infrastructure

Model Registry & Versioning

A centralized repository for storing, versioning, documenting, and governing trained models — the piece of infrastructure that turns "build a model, hand it off" into a repeatable, auditable handoff between data science and operations.

Why a registry exists: two failure stories

Before naming the solution, it helps to feel the pain it fixes — first alone, then at team scale.

Problem statement — 1

A solo data scientist runs experiment after experiment, producing a pile of models and artifacts tracked through whatever naming convention seemed reasonable that week. Because the naming is non-standard, it takes real effort just to find the optimal model again. Once found, the raw artifacts get handed to an ops team — or deployed solo. Either way, ops is left asking: how do I even use this? Has it been tested? What runtime dependencies does it need? What other operational info exists? The whole workflow was "build model, hand it off" — nothing more — so successful collaboration for deployment is genuinely difficult.

Problem statement — 2

The company scales. A data engineer joins, then maybe a product manager. The solo workflow "worked," even though it was painful — but now teammates start asking about model versions, and storing models as loose files stops being manageable. There's no easy way to retroactively fix it. The cross-functional team now needs answers: where's the best version of this model, for audit/test/deployment/reuse? How was it trained? How do we track documentation for compliance and metadata awareness? How do we review models before and after deployment? How do we integrate with the tools and services that make shipping easier?

// field note

This is a standard MLOps pedagogical device — the solo workflow breaking down as team size and shipping cadence grow is widely cited as the core organizational driver behind MLOps maturity models in general, including the Level 0 / 1 / 2 progression covered later in this module. Informal, file-based practices get replaced by standardized infrastructure precisely because they stop scaling with the team, not because they were wrong to begin with.

Introduction: what a registry actually is

An ML model registry is a centralized repository enabling effective model management and documentation. It allows clear naming conventions, comprehensive metadata, and improved collaboration between data scientists and ops teams — the direct fix for both problem statements above. A data scientist pushes trained models into the registry; once there, models are ready to be tested, validated, and deployed to production.

Naming conventions

Every model version gets a clear, standard identity — no more guessing which file is "the good one."

Comprehensive metadata

Training data version, metrics, owner, dependencies — attached to the model, not scattered in someone's notes.

Improved collaboration

Data scientists and ops teams work off the same source of truth instead of an artifact tossed over a wall.

Repository, registry, store, tracking — used loosely, meaning something specific

These four terms get used interchangeably in casual conversation, but they nest inside one another.

TermWhat it actually is
Model RepositoryA storage location for ML models — models as files, nothing more.
Model RegistryA more comprehensive system tracking and managing the full lifecycle of ML models — versioning, metadata, lineage, access control.
Model StoreMay store/fetch models the way a Docker registry does, but delivers the full package: logging, discovery, assets, pipelines, metadata, blueprints for building new models. Examples: ModelStore, ClearML. A model store is a superset of a model registry — the registry lives inside it, and it's the service other systems interface with to retrieve models from that registry.
Experiment TrackingTracks the experiments that feed into (and run alongside) the model registry.

This vocabulary — model store as a superset containing a registry view, cleanly separated from experiment tracking — mirrors how Neptune.ai documents its own product architecture. Nine things a real model registry gives you

Centralized storage, a bridge between experimentation and production, a shared UI, an interface for downstream consumers, versioning, and four distinct integration points across the pipeline — training, staging, CI/CD, and deployment.

1 · Centralized storage for collaboration

One place holding models and artifacts for easy retrieval by apps and services. Without it, artifacts live in scattered files, saved wherever, hard to track. A single view of every model's status across data teams enables real collaboration.

2 · Bridges experiment and production

Acts as the glue between ML experimentation and Ops, letting model development, software development, and ops teams actually collaborate instead of working past each other.

3 · Provides a central UI

Teams search models, view status (staged / deployed / retired), approve or disapprove across stages, and read documentation. Ops can look up validation results and metrics, package if needed, and promote staging → production from one place.

4 · Interface for downstream consumers

Downstream services consume models via API integration, tracking offline/online eval metrics and enabling automated CI/CD/CT setups. The consumer could be a human, an automated job, or a REST endpoint pulling the most stable version.

5 · Enables model versioning

Tracks distinct versions as a model is developed and improved — compare versions, track performance, pick the best one to deploy. (Mechanics detailed below.)

6 · Integrates with experiment mgmt / training pipelines

Accepts raw artifacts (weights, config, metadata) or serialized/containerized models (ONNX, Docker) for production compatibility. Registers the model, assigns a version, notes the training dataset version, adds tags, and pulls params/validation results from the experiment system. Also stores owner, run id, source code version, runtime dependencies, and change history.

7 · Integrates with the staging environment

Staging runs checks and balances — integration testing with other apps, QA before promotion. Reviewers perform fairness checks: explainable results, regulatory compliance, business benefit. Governance/approval workflows and secure access control live here, especially for models trained on sensitive data.

8 · Integrates with CI/CD delivery tools

Custom APIs plug into workflow tools — e.g. webhooks triggering downstream actions on registry events. Configurable promotion: development (training) → staging (testing) → production (serving). Must be highly available to support automated, event- or schedule-based continuous training and delivery.

9 · Integrates with deployment tools

Connects to downstream serving that consumes and serves the model in production; collects real-time or aggregated production metrics — useful for comparing deployed vs. staged models and auditing production models on review.

Versioning, mechanically

Feature 5 above isn't one action — it's a small pipeline of its own, run every time a model changes.

The DevOps-style infinite loop

Feature 2 — bridging experiment and production — is usually drawn as an adapted DevOps "infinite loop." The ML side (Plan → Create → Verify → Package) and the Ops side (Release → Configure → Monitor) both connect through the registry sitting at the pivot, forming one continuous cycle rather than a one-way handoff.

// field note

This feature list mirrors Neptune.ai's "ML Model Registry: The Full Guide," widely cited in MLOps curricula and echoed in the feature sets of MLflow Model Registry, Vertex AI Model Registry, SageMaker Model Registry, and Neptune's own registry. ONNX (Open Neural Network Exchange, Microsoft + Meta, 2017) lets a model trained in one framework run in a different, often faster or more portable runtime. Webhook-based automation (MLflow registry webhooks, Databricks Model Registry webhooks) is the concrete mechanism connecting a registry to external CI/CD systems — turning "Continuous Training" from a buzzword into an automated system. The staging/QA/fairness-gate feature is the practical, registry-level implementation of the SR-11-7-style model-risk-management principles covered in the earlier Model Validation module.

Where the registry fits in the MLOps stack

Running ML projects efficiently at scale almost always needs a registry somewhere in the stack — but exactly what you need from it differs depending on your MLOps maturity level.

Level 0 Manual process

The experimentation output feeds the registry by hand: the data scientist prepares the model artifact and metadata, possibly serializing or containerizing it, before registering it. Ops manually pushes the packaged model to staging for testing, then to a prediction-service engine that integrates with other apps.

Level 1 Continuous training

The goal is continuous training via an automated ML pipeline. The registry enables this well through pipeline integration: the entire pipeline is deployed, its trained model + metadata output feeds the registry directly, it's staged, and — if it passes tests — fed onward to the continuous delivery pipeline for release.

Level 2 Full CI/CD/CT

The registry's role is the same as Level 1, but it's now crucial to a fully automated pipeline: event triggers can promote models with good metrics after retraining on fresh data, or archive models that fall behind — all without a human in the loop.

// field note

This three-level maturity model comes directly from Google Cloud's influential "MLOps: Continuous delivery and automation pipelines in machine learning" whitepaper, one of the most widely referenced MLOps automation-maturity frameworks. Level 0 (notebooks + manual hand-offs) directly echoes Problem Statements 1 & 2. Level 2 — where pipeline components themselves are built, tested, and deployed via full CI/CD — is common at large tech companies operating many models at scale, such as Google, Uber, and Netflix.

Setting up a registry: build, maintain, or buy

The same three-way decision that came up for metadata systems earlier in the course applies again here, now specifically for model registries.

Build

If you understand the key functionality and requirements, you can build it yourself: object storage for models/artifacts, a database for logging model details, API integration for receiving models and promoting them across environments, and a UI for ML teams.

Weigh: Incentive (customization vs. a proprietary license) · Human resources (do you have the skills?) · Time (how long, is the wait worth it?) · Operations (who maintains it long-term?) · Cost (build + maintenance).

Maintain (self-hosted)

Use an existing solution — most are open-source — but manage some features yourself, such as object storage and the database.

Weigh: Type of solution (open-source, no license vs. closed-source, licensed) · Operations (who manages consistent maintenance/updates?) · Cost (infra + running) · Features (already built vs. must build yourself) · Support (community vs. dedicated) · Accessibility (docs quality, ease of getting started).

Buy (fully managed)

The vendor handles operations and management entirely — you just integrate your systems and services with the registry.

Weigh: Industry type (sensitive data, compliance, on-prem needs) · Features (core + workflow extras) · Cost (license vs. feature value) · Security · Performance (latency for large models) · Availability (uptime/SLA) · Support · Accessibility (onboarding, learning curve).

// field note

Same build/maintain/buy trilemma as metadata systems, applied to a different layer. In practice: large tech companies with unique scale needs (Uber, Netflix, Meta) have historically built custom in-house registries; many mid-sized orgs adopt open-source MLflow Model Registry to avoid both a from-scratch build and vendor lock-in; orgs prioritizing speed-to-value or lacking MLOps capacity often buy a fully managed solution — AWS SageMaker Model Registry, Google Vertex AI Model Registry, Azure ML Model Registry, or Neptune.ai.

01 Where this whole lecture starts

Big data isn't more data — it's a different way of working with it

A single machine and a single database ran out of room. Everything in this lecture — distributed storage, parallel processing, Hadoop, Spark, streaming, cloud platforms — exists because of that one fact.

What is big data?

Massive, complex data sets that traditional data management systems cannot handle. It's not just volume — it's an intricate ecosystem of technologies, methodologies, and processes built to capture, store, manage, and analyze data at a scale no single machine can hold. A shop owner's notebook of receipts is fine for a traditional database; Amazon tracking every click, purchase, and page view from hundreds of millions of shoppers every second, worldwide, is not.

// field note

IBM characterizes big data along volume, velocity, and variety — data sets too large or complex for traditional processing software. Big data adoption accelerated through the 2000s/2010s as storage costs fell and digitally-generated data (web clicks, sensors, mobile, social) exploded — the exact wave that motivated Google's GFS/MapReduce, and later Hadoop, covered later in this deck. (ibm.com/think/topics/big-data)

The V's of big data

A checklist for what makes data "big" and hard to work with, beyond sheer size.

Volume

How much data — petabytes, not megabytes. Cloud storage helps organizations manage ever-larger datasets so information isn't lost to storage limits.

Velocity

How fast it arrives — real-time social updates, high-frequency trading. Stream-processing and in-memory systems capture, analyze, and act on it in near real time.

Variety

How many shapes it comes in — structured, unstructured (text, images, video), semi-structured (JSON, XML). Managed with NoSQL databases and schema-on-read data lakes.

Veracity

Can you trust it — noise, duplicates, missing fields, collected automatically at scale. Addressed with cleaning, validation, and verification tools.

Value

Does it actually help — the real-world benefit extracted via analytics, ML, and AI. Collecting data is pointless if you can't turn it into a decision.

// field note — origin of the V's

The original 3 V's (Volume, Velocity, Variety) were coined by Gartner (then META Group) analyst Doug Laney in a 2001 note, "3D Data Management" — years before "big data" became a mainstream term. Veracity was added by IBM and others around 2012; Value followed as a business-outcome framing. Some models now extend to 5–7 V's. (techtarget.com/whatis/definition/3Vs)

Traditional analytics vs. big data analytics

The "old way vs. new way" cheat sheet. Traditional analytics designs a rigid schema up front and moves data to the analysis tool; big data analytics keeps schema flexible (schema-on-read) and moves the analysis to the data instead — the same "data locality" idea that recurs throughout this deck.

// field note — why ETL became ELT

The ETL → ELT shift is tied to cheap, scalable cloud storage (S3, ADLS, GCS): once storage got radically cheaper than compute, it became economical to dump raw data first and defer transformation until it's actually needed — the pattern underlying data lakes and modern cloud platforms like Snowflake, BigQuery, and Databricks (Section 10). (ibm.com/think/topics/big-data-analytics)

How big data analytics works — the five-step pipeline

Nearly everything else in this lecture zooms into one of these five boxes.

1 · Collection

From sensors, social media, and more — often too large for one machine, and structured, semi-structured, or unstructured.

2 · Storage

Stored in a distributed file system such as HDFS (Section 6), enabling later processing.

3 · Processing

Specialized tools — MapReduce and Spark (Sections 7–8) — extract insight from the stored data.

4 · Analysis

Statistics, ML, and visualization find trends and patterns in the processed data.

5 · Results

Insights inform business decisions, or generate reports and dashboards for stakeholders.

Big data analytics in the wild

eCommerce & Retail

Amazon tailors personalized advertising, forecasts demand, segments customers, prices dynamically, and detects fraud — all from click/search/purchase data at massive scale. Its item-to-item collaborative filtering ("customers who bought X also bought Y") became a model widely imitated across e-commerce.

HealthCare

Ginger.io (an MIT startup) uses smartphone signals — messaging frequency, calls, sleep, exercise — as a passive early-warning system for mental health: decreased communication may flag depression, increased calls/messages may flag mania in bipolar patients.

Manufacturing

KIA Motors monitors vehicle sensor data to catch failure patterns before they happen (predictive maintenance) and optimizes supply chain via inventory, demand, and logistics data.

// field note — myth-busting

Big data analytics is not meant to replace RDBMS or data warehouses, and it isn't only for big data companies. It's a complement: traditional systems still fit structured, transactional, well-understood data; big data tools step in specifically when data outgrows what those tools can efficiently handle.

Understanding this story intuitively means understanding the motivation for everything that follows.

03 Two different bets on how machines cooperate

Shared memory, tightly coupled — or independent machines, loosely coupled

Parallel systems trade scale and resilience for raw speed. Distributed systems trade speed for scale and resilience — and at big-data scale, resilience wins.

The core distinction

In parallel computing, several processors sit inside the same machine and share one memory pool — several chefs in one kitchen sharing one pantry. In distributed computing, each machine has its own processor and memory, and they talk over a network — independent kitchens in different cities, coordinating by phone calls (network messages) to cook one big meal together.

// field note

This shared-memory vs. distributed-memory split is foundational in computer architecture (Flynn's taxonomy; shared- vs. distributed-memory multiprocessors). Most "big data" systems (Hadoop, Spark) run on distributed-memory architectures precisely because they must scale far beyond one machine's shared memory bus; GPUs and multi-core CPUs remain classic shared-memory parallel systems within a single node. (cloud.google.com/learn/what-is-apache-spark)

Five dimensions, one clear pattern

Distributed systems trade speed for scale and resilience; parallel systems trade scale and resilience for speed.

// field note — why this matters for the rest of the lecture

This tension is exactly what motivated Google's GFS and MapReduce papers: designed for a world where component failures are the statistical norm across thousands of commodity machines, with fault tolerance (replication, automatic re-execution) built into the software layer rather than relying on expensive, failure-proof hardware. That philosophy carried directly into Hadoop's HDFS and MapReduce — both covered next. (research.google.com/archive/mapreduce-osdi04.pdf)

04 The pantry next to the stove

RAM is ~100,000× faster than disk — that gap is why Spark exists

A chef who keeps ingredients in a nearby pantry cooks a lot faster than one who walks to a basement storeroom for every single item.

Disk-based computing

Data lives persistently on SSDs/HDDs and is loaded into RAM only when needed — every access is a round trip to the basement storeroom. Access speed: milliseconds.

In-memory computing (IMC)

Data resides primarily in RAM, eliminating slow disk I/O and processing at memory speed — ingredients kept in the pantry right next to the stove. Access speed: microseconds.

Main memory reference ≈ 100 ns : Disk seek ≈ 10 ms → ~100,000× gap
// field note

This latency gap is one of the most cited numbers in computer science — from Jeff Dean's "Numbers Everyone Should Know" talks at Google. It's the fundamental physical reason in-memory systems like Apache Spark, SAP HANA, and Redis can be orders of magnitude faster than disk-oriented systems like classic Hadoop MapReduce, especially for iterative or interactive workloads. (cloud.google.com/learn/what-is-apache-spark)

In-memory computing for big data

Two of the V's get solved by two different tools: Volume and speed are addressed by keeping working data in RAM (IMC); Variety — unstructured/semi-structured data that doesn't fit relational tables — is addressed by NoSQL databases. Falling RAM prices over the past two decades made keeping large working datasets entirely in memory across a cluster economically feasible, where it would once have been cost-prohibitive.

05 Cheap machines, treated as one giant computer

Hadoop: the "operating system" of big data

Not literally an OS — a foundational open-source layer that lets a cluster of ordinary, inexpensive computers act as one giant storage and compute system.

What Hadoop is

An open-source framework for storing huge amounts of data, managing it via distributed storage and parallel processing, and running applications on clusters of commodity hardware. Its main advantage: handling structured, unstructured, and semi-structured data in huge volumes, making collection, processing, and analysis easier and more flexible than traditional processors allowed.

// field note — origin story

Hadoop was created by Doug Cutting and Mike Cafarella, split out of the Apache Nutch crawler project in January 2006, and named after Cutting's son's stuffed yellow toy elephant — hence the logo. Yahoo hired Cutting in 2006 and drove early development; by 2008, Yahoo's production search index ran on a 10,000-core Hadoop cluster, before Hadoop was donated fully to the Apache Software Foundation. (hpcwire.com/bigdatawire/2015/04/15/from-spiders-to-elephants-the-history-of-hadoop)

The ecosystem, as a stack

HDFS is the foundation (storage), YARN is the traffic-management layer (who gets which resources, when), and everything else — Hive, Pig, Spark, HBase, Kafka, and more — is a specialized tool built on top.

What each piece does

Storage

HDFS stores files; HBase is a distributed NoSQL database built on top of HDFS.

Processing engines

MapReduce — original, disk-based. Spark — newer, in-memory, much faster.

Querying

Hive (SQL on structured/batch data), Drill (flexible semi-structured queries), Pig (scripting, "Pig Latin").

Ingestion

Flume moves large volumes of log/unstructured data in; Sqoop transfers structured data between RDBMS and Hadoop.

Streaming

Kafka — the messaging backbone. Storm — real-time stream and complex event processing.

Machine learning

Mahout — older, standalone. MLlib — built into Spark.

Search

Lucene — underlying full-text search library. Solr — enterprise search platform built on Lucene.

Ops & coordination

Zookeeper syncs distributed components; Oozie schedules multi-step workflows; Ambari provides a management/monitoring dashboard.

Resource management

YARN (Yet Another Resource Negotiator) decides who gets CPU/memory and when — introduced in Hadoop 2.0 specifically so non-MapReduce engines like Spark could share the same cluster.

// field note — tools that outgrew Hadoop

Several ecosystem tools became bigger than Hadoop itself: Kafka (created at LinkedIn ~2010–2011 by Jay Kreps, Neha Narkhede, and Jun Rao) is now the de facto event-streaming standard industry-wide, independent of Hadoop — its creators later founded Confluent. Spark (Section 8) similarly outgrew its Hadoop-ecosystem origins to become a general-purpose engine usable with or without HDFS. Lucene/Solr predate Hadoop and were created by the same person, Doug Cutting, whose search-indexing work directly shaped his later thinking about distributed processing. (edureka.co/blog/hadoop-ecosystem)

06 One librarian, many storage rooms

HDFS: split the file into blocks, copy every block, survive any one failure

A director/worker architecture where the director never holds a single byte of actual data — only the map of where everything lives.

NameNode — the director

One per cluster. Tracks the status of every file, file permissions, and the location of every block. Manages the file-system namespace and controls client access — opening, closing, renaming.

DataNode — the worker

Manages block creation, deletion, and replication, plus read/write requests. Each stores its blocks as separate files on its own local disk. Runs on commodity hardware to keep cost down.

How data moves through it

Data is broken into blocks and distributed across the cluster; blocks are replicated onto other nodes so they can be processed in parallel and survive node failure — removing one copy never risks corrupting the file. HDFS provides a native Java API, a C-language wrapper, and an HTTP browser interface for access.

// field note

HDFS closely reimplements Google's proprietary Google File System (GFS), described in Ghemawat, Gobioff, and Leung's 2003 SOSP paper. Both use the same master/worker split (NameNode/DataNode ↔ master/chunkserver) and the same "replicate each block onto multiple machines" fault-tolerance strategy — GFS defaults to 3 replicas, and HDFS follows the same default. (ibm.com/think/topics/hdfs)

Worked use case — a nationwide phone directory

Surnames starting with A live on server 1, B on server 2, and so on. Reconstructing the whole directory needs blocks from every server — that's the block-distribution model. To survive a server failing, HDFS replicates each piece onto two more servers by default — three copies total. Redundancy can be raised or lowered per file or environment (a dev cluster typically skips it). The same split also lets the cluster run jobs on all servers in parallel, and keeps computation next to the data it needs (data locality).

Default replication factor = 3 (1 original + 2 copies)
07 Two functions, run at massive scale

Map, Shuffle, Reduce — the pattern behind almost every big-data aggregation

A 10-hour single-machine job split across 10 machines can, in the best case, finish in about an hour — the entire value proposition in one sentence.

The two tasks

Map takes raw data and converts it into key/value pairs. Reduce takes the mapped outputs, aggregates all values sharing a key, and produces a final set of key/value pairs. In between, Shuffle sorts and routes every pair so everything sharing a key lands at the same reducer — the "traffic control" step that makes the aggregation correct.

1 processor, 10 hours → 10 processors in parallel, ~1 hour (ideal case)

Worked example — word count

Input: "Deer Bear River / Car Car River / Deer Car Bear"

// field note

MapReduce was introduced by Google's Jeffrey Dean and Sanjay Ghemawat in their 2004 OSDI paper, directly inspired by functional programming's map and reduce/fold primitives — hiding parallelization, fault tolerance, and load balancing from ordinary programmers, who only write the Map and Reduce functions. Google's own production use included generating its web search index from 20+ terabytes of crawled documents via five to ten chained MapReduce jobs. (research.google.com/archive/mapreduce-osdi04.pdf)

Second worked example — maximum temperature per city

The reduce function is what changes: sum becomes max. Records like <Tokyo,38> are scattered across input files; shuffling groups every city's readings together; each reducer keeps only the highest value for its city.

// field note

This only works because shuffling guarantees every one city's records land at the same reducer — split across two reducers, neither would see the true maximum. This is a close variant of the "weather dataset" example popularized by Tom White's Hadoop: The Definitive Guide, using real NOAA station data. (ibm.com/think/topics/mapreduce)

08 The same idea, minus the disk round trips

Apache Spark: keep the half-finished dish on the counter

MapReduce writes every stage's output back to disk before the next stage reads it. Spark keeps it in memory — a modest win for one pass, a massive one for anything iterative.

// field note

Spark was created by Matei Zaharia starting in 2009 at UC Berkeley's AMPLab specifically to fix this weakness, open-sourced in 2010, donated to Apache in 2013. Its core abstraction, the Resilient Distributed Dataset (RDD) — Zaharia et al.'s 2012 NSDI paper — lets data be cached in memory across a cluster while staying fault-tolerant via lineage: Spark remembers how each RDD was derived, so it can recompute a lost partition rather than needing disk replication. (en.wikipedia.org/wiki/Apache_Spark)

Low-latency queries

Cache the working dataset in memory once, then run many different queries against it at memory speed — ask a question, get an answer in seconds, ask another.

Iterative computations

Subsequent iterations reuse the same in-memory data instead of re-reading from disk each pass — exactly what ML training loops (e.g. gradient descent) need.

Spark's ecosystem

Spark Core handles memory management, fault recovery, scheduling, and cluster monitoring; four libraries sit on top, sharing the same RDD/DataFrame abstraction so they can be mixed in one program.

Spark Streaming

Real-time processing of live data streams.

MLlib

Machine learning at scale.

Spark SQL

Query via SQL or HiveQL over Spark's engine.

GraphX

Graph & graph-parallel computation.

// field note

Each library has its own Berkeley AMPLab paper: Spark Streaming's D-Streams (2012 HotCloud), Spark SQL (from the earlier Shark project, formalized in a 2015 SIGMOD paper), and GraphX (2014 OSDI). This shared-engine-plus-specialized-libraries pattern is a key reason Spark displaced many single-purpose tools that had proliferated in the Hadoop ecosystem. (spark.apache.org/research.html)

Architecture: Driver, Cluster Manager, Workers

Your program becomes the Driver, running on the master node; its first act is creating a Spark Context — a "gateway to all Spark functionality," like opening a database connection. The Spark Context hands the job to the Cluster Manager, which splits it into Tasks distributed across Worker nodes, each executing its slice of the partitioned RDD and caching data in memory for reuse. More workers means both more parallelism and more total cache memory.

// field note — lazy evaluation & DAGs

Spark builds a Directed Acyclic Graph (DAG) of every requested transformation but doesn't execute anything until an "action" (like .count() or .collect()) triggers it — like planning an entire road trip's route before driving, rather than deciding turn-by-turn. Because Spark sees the whole plan up front, it can optimize it. DataFrames add a schema on top of raw RDDs, enabling further rewriting via the Catalyst optimizer — similar to how a SQL database's query planner works. This driver/cluster-manager/worker model runs unchanged whether the underlying manager is Spark's own Standalone manager, YARN, Mesos, or Kubernetes — letting Spark run on an existing Hadoop cluster or entirely independently on cloud infrastructure. (spark.apache.org/research.html)

09 From batch-adapted to streaming-first to AI-native

Five frameworks, five different bets on latency vs. flexibility

Latency drops and Python-native, ML-focused flavor increases as you move from Spark toward Flink, Ray, and Dask — a real industry shift toward real-time and AI-native workloads.

Spark Streaming (DStreams)

Treats a live stream as a rapid sequence of small micro-batches, built on RDDs — so MLlib, Spark SQL, and the DAG optimizer all work on streaming data with barely any changes. Sources include Kafka, Flume, Kinesis; output to file systems, databases, dashboards.

Structured Streaming

Production-ready since Spark 2.2. Treats an incoming stream as an infinitely growing table: write one batch-style query, and Spark incrementalizes it — recomputing only the update at each trigger, not the whole table.

// field note

D-Streams were formalized in a 2012 HotCloud paper, trading a small micro-batch-window latency for the same fault-tolerance/load-balancing benefits as Spark's batch model. Structured Streaming's "unbounded table" model closely parallels the Google Dataflow model (basis for Apache Beam) — a broader convergence around unifying batch and streaming semantics under one query abstraction. (databricks.com/glossary/what-is-spark-streaming)

Apache Flink — true event-at-a-time streaming

Where Spark Streaming is fundamentally a batch engine adapted for streaming, Flink was built streaming-first: it processes each event individually the instant it arrives, with sophisticated out-of-order/late-event handling (event-time processing) and exactly-once state-consistency guarantees even through machine failures.

// field note

Flink originated as the Stratosphere research project at TU Berlin (2009), renamed and entering the Apache Incubator in 2014. Several creators later founded Data Artisans (renamed Ververica after Alibaba's 2019 acquisition). Flink is the streaming engine of choice at Alibaba, Netflix, Uber, and Stripe for genuinely low-latency, stateful use cases like fraud detection. (textql.com/wiki/apache-flink)

Ray — Python functions and classes, distributed

Three primitives: a Task runs a stateless function remotely; an Actor is an instance of a class that keeps persistent state between calls (useful for online learning or simulations); an Object is shared data referenced across the cluster without needless copying. This flexibility makes Ray the go-to for AI workloads that don't fit a "big static dataset" mold — reinforcement learning, distributed LLM training.

Task

Stateless — run this function elsewhere, give me the result.

Actor

Stateful — run this class elsewhere, keep it alive between calls.

Object

Shared value in Ray's in-memory object store, referenced across nodes.

// field note

Ray originated in 2016 at UC Berkeley's RISELab (successor to the AMPLab that created Spark), purpose-built for reinforcement learning workloads Spark handles poorly — heterogeneous CPU/GPU allocation, stateful actors, fine-grained low-latency scheduling. OpenAI has publicly used Ray to coordinate RLHF-style training used in models like ChatGPT. (bair.berkeley.edu/blog/2018/01/09/ray)

Dask — scale the Python you already know

Collections (Array, DataFrame, Bag, Delayed, Futures) generate a task graph, executed by a scheduler (threads/processes locally, or a distributed cluster). A Dask DataFrame behaves like a giant Pandas DataFrame but is actually many smaller DataFrames spread across a cluster, with Dask figuring out how to run .groupby() or .mean() across all the pieces in parallel.

// field note

Created by Matthew Rocklin, first described at SciPy 2015. Unlike JVM-based Spark/Flink, Dask is a native Python library integrating directly with NumPy, Pandas, and scikit-learn — popular with data scientists who want to scale existing code without a rewrite. (dl.acm.org/doi/10.5555/3291168.3291210)

10 The same ideas, delivered as a service

No hardware to rack, no cluster to manage — just storage and compute as a service

Everything before this section required buying, racking, and operating physical servers. Cloud-native platforms remove that burden and charge only for what's actually used.

What a cloud data platform is

An integrated suite of cloud services to collect, store, process, analyze, and act on data at scale — combining storage, compute, and analytics under pay-as-you-go pricing, with elastic scalability and no physical infrastructure to manage.

Snowflake

Separates storage from compute entirely — one pool of stored data, multiple independent Virtual Warehouses reading from it without contention. Multi-cloud (AWS/Azure/GCP), strong encryption and RBAC. Best for self-service BI and secure cross-team/partner data sharing.

BigQuery

Fully serverless — submit SQL, pay per data scanned, no cluster to provision. Built on Google's Dremel (query engine), Colossus (storage), Jupiter (network), and Borg (compute, Kubernetes's precursor). BigQuery ML runs ML models via plain SQL. Best inside an existing Google Cloud stack.

Databricks

Combines Spark's processing power with Delta Lake's reliability into a "lakehouse" — a data lake's flexibility with a warehouse's ACID transactions and schema enforcement. Founded by Spark's own creators; strong for collaborative data science/ML with integrated notebooks.

// field note

Snowflake was founded in 2012 by Benoit Dageville, Thierry Cruanes, and Marcin Żukowski — its storage/compute separation directly solved the "noisy neighbor" contention problem of earlier shared-cluster warehouses. BigQuery's Dremel was first described in Google's 2010 VLDB paper, and heavily influenced Apache Drill and the Parquet columnar format; Colossus is GFS's successor (Section 6). Databricks was founded in 2013 by the original AMPLab Spark team (Matei Zaharia, Ali Ghodsi); Delta Lake was open-sourced in 2019 to close the reliability gap between raw lakes and structured warehouses. (rudderstack.com/blog/cloud-data-platform)

11 The capstone question

It's not batch OR streaming — it's batch AND streaming, at different points in the ML lifecycle

Train on batch. Serve on stream. Most production ML systems need both families of tools this lecture covered.

Batch processing

Bounded input, a job runs over it, output is produced. Success measured by throughput and data quality. Runs on a schedule — and because it accumulates data before processing, it introduces latency. This is exactly what MapReduce and traditional Spark jobs are built for.

Stream processing

Consumes and produces continuously, operating on small, immutable "events" shortly after they occur, often via a broker like Kafka. Near-real-time, but a harder fault-tolerance problem — input never stops arriving, so failure recovery happens while data keeps flowing.

Deciding between them: the time value of data

If the business value of your data decays sharply within minutes of being emitted, batch is the wrong first choice. But most decision-making doesn't happen second-to-second — replicating a database, building reports, updating dashboards are all served fine by batch.

// field note — Lambda vs. Kappa

Lambda architecture (Nathan Marz) runs separate batch and speed/streaming layers side by side, merging results — extra complexity for both deep historical accuracy and low-latency freshness. Kappa architecture (Kafka co-creator Jay Kreps, 2014) simplifies this by treating all data, including historical reprocessing, as a single continuous stream — avoiding two parallel codebases. (kai-waehner.de/blog/2021/09/23/real-time-kappa-architecture-mainstream-replacing-batch-lambda)

Where each paradigm fits in the ML lifecycle

StageParadigmWhy
Initial trainingBatchNeeds a large, bounded historical dataset and heavy iterative computation
Batch inferenceBatchPredictions needed by a scheduled deadline, not instantly — e.g. daily sales forecasts
Continuous / online trainingStreamingModel adapts to fresh patterns without waiting for a full retraining cycle
Real-time inferenceStreamingPrediction value collapses within minutes — fraud detection, live recommendations
// field note

This batch-for-training, streaming-for-serving pattern is widely recognized MLOps best practice, closely paralleling Lambda architecture: a batch layer for deep historical accuracy (training on the full dataset), a speed layer for immediate results (real-time inference), both feeding a combined serving outcome.
